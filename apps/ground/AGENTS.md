# AGENTS.md: apps/ground

`sat-teleop-ground` (L3) is the ground adapter's entry point. It stays thin: config loading, wiring over `sat-teleop-control` (MAVLink, controller, camera) and `sat-teleop-media` (the freshness output) and a small HTTP client for its own lease endpoints, with `sat_teleop_media::metrics::serve_with` for `GET /metrics` and those endpoints.

- `sat-teleop-ground run --config <toml> --limits <toml> --metrics-addr <addr>` resolves the ground stations and the video destinations (first IPv4 address each; failure exits), runs the freshness output, the MAVLink bridge (which, with `camera_uri`, also answers as the camera) and the controller on threads and serves HTTP on the main thread. If the endpoint cannot bind, the process exits.
- HTTP on the metrics address: `GET /metrics`; `POST /lease` asks the vehicle for the control lease and answers with the status once the vehicle has granted it and its first challenge has arrived, so a command sent right after goes out (200 held, 409 denied, 504 no answer within 3 s, 503 before the control socket is up, 502 if sending failed); `DELETE /lease` gives it back; `GET /status` reports it. Requests are handled one at a time, so a lease request holds the others for up to 3 s. Every route, `GET /metrics` included, needs the bearer token of `--token-file` (the CLI subcommands take the same global flag, and `--job-token-file` is the relay's job API token for `detail`: the ground's token is never presented to the relay); without a token it listens on 127.0.0.1 only. A grant without a challenge within 3 s answers 504, never 200.
- `sat-teleop-ground take-control | release-control | status [--adapter <url>]` call those endpoints on a running adapter (default `http://192.168.233.30:9100`), print the JSON answer and exit 1 on a non-2xx status. `just take-control`, `just release-control` and `just control-status` run them in the `ground` container.
- `sat-teleop-ground run [--relay <url>]` with `--job-token-file` also runs `src/box_detail.rs`: while the camera has a tracked box it requests a crop of where the vehicle reports it now (`Camera::target`; the drawn box until it reports one) (`inset::widen`) from the newest retained snapshot every 4 s through the relay's job API, one job in flight, frees the job, decodes and scales the crop (`media::inset::Image`) and puts it in the `DetailCell` the output draws from, with `Camera::detail_received` for the tracking status. A failed request is logged and the next one is 4 s later; without a job token it does not run.
- `sat-teleop-ground detail request (--ago-s <n> | --at-ms <unix ms>) [--crop x,y,w,h] [--max-bytes <n>] [--expires-s <n>] [--relay <url>]` asks the relay's job API (default `http://192.168.232.20:8080`, on `ground_net`) for the retained frame at or before that time, whole or cropped (fractions of the picture), and prints the job id; `detail fetch <id> -o <file>` waits for the object, writes the JPEG and prints it labelled as historical (the retained frame's id and capture time, its age by this machine's clock, the crop and the source size), then frees the job; `detail cancel <id>` cancels it. `--ago-s` uses this machine's clock, which agrees with the vehicle's capture clock only where the clocks agree (`docs/measurement.md`); `--at-ms` is exact. The code is `src/detail.rs`.
- Config: `testbed/config/ground.toml` (`listen` overlay address for mavlink-router's telemetry, `relay` mavlink-router's overlay address, `gcs` list of `host:port`, `control` the controller's overlay socket, `vehicle` the vehicle's control endpoint, `control_key` the signing key of its envelopes and lease messages, `vehicle_id` the vehicle's name (`vehicle_id` of the vehicle's config: signatures are made for it), `clock` (`"chrony"`, `{ chrony_at = "<host>" }` (a container reading its host's chronyd command port, `deploy/ground/chrony-ground.conf`), `"shared"` or `{ fixed = <ms> }`, which ends when the wall clock steps by more than it: this machine's clock bound; the vehicle's reported bound is added, and the output judges the video's age by the sum, which is `AgeUnknown` unless both are fresh; `GET /metrics` shows `clock`), and `[camera]`: `hfov_deg`, the camera's horizontal field of view in degrees (0 to 180, exclusive), which switches the predictive display on (none without the table), and `[video]`: `source` RTSP URL, `destinations` list of `host:port`, `camera_uri` (no camera without it) and `[video.encoding]`, a rung); unknown keys are rejected. Limits: `[control]` and `[freshness]` of `testbed/limits.toml`. In the testbed, metrics listen on `192.168.233.30:9100`.
- Until `wg0` is up the overlay addresses cannot be bound; the bridge and the controller retry every second and report `listen.up` and `control.link.up` false with the error meanwhile. A restarted adapter starts without a lease and never takes one on its own.
- Metrics JSON: `listen` (link state), `relay_endpoint` (where mavlink-router was last heard from), `telemetry` (mavlink-router to the stations), `gcs` (the stations' frames; out counts only the read-only ones forwarded raw), `control`: `link`, `status` (as `GET /status`), `wrapped` by kind (`keepalive`, `liveness`, `continuous`, `discrete`), `no_lease` (heartbeats and `MANUAL_CONTROL` dropped without a lease), `denied` and `unsupported` (commands the adapter answered itself), `refused` by message, the vehicle's `results` (`applied`, `repeated`, `rejected`, `unsupported`) and `vehicle_rejected` by reason, `send_failed` and `ignored`; `camera` (`null` without one): `heartbeats`, `answered` by message, `unsupported`, `dropped`; and `video`: the `source` and `output` pipelines' health, `decoded`, `unreadable`, `new_frames`, `decode_age_ms_total` (the new frames' ages at decoding, summed), `pushed`, `repeated`, `late` (frames dropped on their way out because the state they showed had stopped being true), the current `state`, frames sent by state (`states`), `rtp_packets` and `rtp_bytes` sent.

Use `anyhow` with `.context()`. Bridging belongs in `sat-teleop-control`. Documented in `docs/testbed.md` and `docs/qgc.md`.

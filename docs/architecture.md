# Architecture

This describes how the system is built and what each part does today. The plan and status are in [issue #2](https://github.com/oscnord/sat-teleop/issues/2); research background is in [issue #1](https://github.com/oscnord/sat-teleop/issues/1). Where a part has run only in containers or has never run on hardware, the text says so.

## Current state

- Cargo workspace: resolver 3, edition 2024, Rust 1.99.0, workspace lints (`unsafe_code = "forbid"`, Clippy pedantic plus panic denies).
- `sat-teleop-xtask`: `cargo xtask layers` and `cargo xtask fixtures [--check]`.
- Fixture manifest with one pinned clip (`foreman_cif.y4m`).
- `sat-teleop-lab` and `sat-teleop-lab-cli` (`lab`): impairment profile format and validation, pure `tc` translation, the router agent (`lab router`) and `lab impair`, seven synthetic profiles in `testbed/profiles/`.
- Compose testbed (project `sat-teleop`): router with NAT and filtering, network sidecars for vehicle, relay, ground and checks with `ctl_net` filtered down to orchestration and metrics, the WireGuard overlay with keys from `just lab-keys`, and `lab check boot` with the `lab check` results contract. The live video path runs in it: `companion`, `relay` and MediaMTX (RTSP path `live`, published on host loopback). ArduRover 4.7.2 SITL (`sitl`) runs in the vehicle namespace, its ports kept to loopback, and mavlink-router in the relay namespace. See `docs/testbed.md`.
- `sat-teleop-policy` (L0): the in-picture stamp (`stamp`), which draws frame identity and capture time into the luma plane and reads them back, with the state stamp the ground output draws below it; a byte-rate token bucket that refuses bulk traffic before preferred traffic (`rate`); the uplink budget (`budget`) and the adaptation ladder with its controller (`adapt`); the control lease with challenge freshness, sequence rules, a latest-only continuous setpoint and a discrete transaction cache (`control`); the classification of video freshness (`freshness`); retention of retained snapshots (`retention`) and when retrieval may send (`retrieval`). Details in `crates/policy/AGENTS.md`.
- `sat-teleop-media` (L1): the vehicle sender (test pattern or looped y4m clip, stamp, x264, RTP, its rung changed while it runs, and test-only pause and freeze), the relay ingress (jitter buffer, RTSP publish to MediaMTX) and its answers to the vehicle's probes, the vehicle's adaptation loop, the headless receiver `lab` measures with, and the ground's freshness output (decode, state stamp and overlay, re-encode, RTP to QGC); typed pipeline errors, restart supervision and the `GET /metrics` endpoint. `sat-teleop-vehicle`, `sat-teleop-relay` and `sat-teleop-ground` (L3) run them with `testbed/config/*.toml`. See `crates/media/AGENTS.md`.
- `sat-teleop-control` (L1): MAVLink frames read and checked with the `mavlink` crate (`ardupilotmega` dialect, which includes `common`); the vehicle bridge between SITL and mavlink-router: telemetry within a byte budget (`testbed/limits.toml`), bulk messages dropped first, and a gate that admits only read-only traffic raw; the control envelope protocol (below) with the vehicle's control endpoint and the ground's controller. `sat-teleop-vehicle` runs the bridge next to the sender. The ground bridge in `sat-teleop-ground` (L3) passes telemetry from mavlink-router to QGroundControl on the Mac and to `checks`, forwards their read-only traffic raw and is their only command endpoint, with `take-control`, `release-control` and `status` on its `ctl_net` HTTP endpoint; it also answers the stations as the vehicle's camera, announcing the freshness output. ArduRover SITL loads `testbed/sat-teleop.parm` over the pinned defaults (GCS failsafe, RC override timeout). See `crates/control/AGENTS.md` and `docs/qgc.md`.
- `lab check mavlink`: heartbeat rate, `REQUEST_MESSAGE` round trip, telemetry rate, a forced arm the adapter denies without the lease, SITL's ports closed to the overlay, and a forwarding cut and recovery of telemetry, with `checks` acting as a ground station. See `docs/measurement.md`.
- `lab check control-freshness`: invalid envelopes from a second controller refused with nothing applied, one lease for two controllers, discrete command acknowledgement times and continuous setpoint delay through the adapter, and either SITL stopping after the adapter is killed mid-drive or nothing sent into a 10 s blackout running afterwards and control needing the lease again. See `docs/measurement.md`.
- `lab check skeleton`: frame age, new-frame cadence, uplink rate, forwarding cut and recovery of the live video path, graded against `perf/budgets.toml`. See `docs/measurement.md`.
- The ground's freshness output in `sat-teleop-ground`: MediaMTX's stream decoded, each frame marked Live, LowRate, Stale, Frozen, Disconnected or AgeUnknown (overlay text and a state stamp), re-encoded and sent to QGC over local UDP, a repeat of the last frame only when nothing went out for two frame periods or the state is about to change; the adapter announces it as the vehicle's camera (MAVLink component 100), which QGC 5.1.5 plays without configuration (`docs/qgc.md`). With `[camera] hfov_deg` the output also draws the predictive display (below), and, while the pilot's box is tracked, the newest crop of it as a labelled `DETAIL` inset ("Regional video"). `lab check qgc-status`: the camera's answers, the output's state while healthy, after a pause, a freeze and a blackout of the link, and recovery, and the latency the output adds. See `docs/measurement.md`.

- Retained detail: the sender tees its full-resolution frames to a snapshot branch (`sat-teleop-media`), the vehicle keeps them as JPEG files in a bounded store (`sat-teleop-detail`, retention in `sat-teleop-policy`), and the ground asks the relay for a snapshot or a crop of the frame captured some seconds ago, which the vehicle uploads at lower priority than live video and control (`sat-teleop-ground detail`). `lab check recording` and `lab check retrieval`. See "Retained detail" below and `docs/measurement.md`.

- Adaptation: the vehicle probes the relay every 250 ms, and `sat-teleop-policy`'s controller walks the ladder in `testbed/ladder.toml` from the answers, latency first, with the uplink budget setting the telemetry cap too; see "Adaptation" below. `lab check adaptation`: the offered uplink under each downward step of `bandwidth-steps`, the frame age's recovery, rung changes per minute and time per rung group, and a second viewer leaving the uplink as it was. See `docs/measurement.md`.

- Camera ingest and the webcam demo: the sender's `ingest` source decodes RTP/H.264 from a camera outside the container (`sat-teleop-media`, source-address filter and decode timing included) before the stamp, `ingest_net` carries it to the vehicle's one port and nothing else, `just demo <profile>` streams the Mac's camera through it and `just ingest-check` grades it with a test-pattern feeder (`docs/demo.md`).

- Real hardware (never run on hardware, `docs/pi.md`, `docs/deploy.md`): the sender's V4L2 (USB webcam, MJPEG or YUYV) and libcamera sources, the choice of `v4l2h264enc` with `x264enc` as the fallback and `sat-teleop-vehicle probe-camera` (`sat-teleop-media`); the vehicle's autopilot link over a serial port (`sat-teleop-control`); provisioning, a systemd unit, config templates and compose files for a Pi, a relay server and a ground machine, and the recipes that build and package them (`deploy/`).
- SITL identification: control frames reach the autopilot only after it has identified itself as a simulator, and a normal flight controller build gets only the read-only traffic ("Control protocol").

## Layers and ownership

Each package lives in a short directory; package names use the `sat-teleop-` prefix. All are registered in `xtask/src/layers.rs`, which `cargo xtask layers` enforces. `sat-teleop-xtask`, `sat-teleop-policy`, `sat-teleop-media`, `sat-teleop-control`, `sat-teleop-detail`, `sat-teleop-lab`, `sat-teleop-vehicle`, `sat-teleop-relay`, `sat-teleop-ground` and `sat-teleop-lab-cli` exist today.

| Layer | Package | Dir | Owns |
|---|---|---|---|
| L0 | `sat-teleop-policy` | `crates/policy` | Pure decisions: adaptation ladder and hysteresis, control lease and freshness, bandwidth allocation, recording quota and eviction, the in-picture stamp. No I/O, no clock, no GStreamer, MAVLink, HTTP, filesystem or sockets. |
| L1 | `sat-teleop-media` | `crates/media` | GStreamer pipelines, frame identity, RTP/RTCP integration, media feedback, ground freshness output, snapshot encoding. |
| L1 | `sat-teleop-control` | `crates/control` | MAVLink integration, command wrapping and vehicle gate, ACK correlation, telemetry limits, control envelope sockets. |
| L1 | `sat-teleop-detail` | `crates/detail` | Retained snapshot store and index, restart recovery, the bounded HTTP job API (relay side), the vehicle's retrieval worker and the API's client. The job API has no authorization (`Retained detail`). |
| L2 | `sat-teleop-lab` | `crates/lab` | Profiles, `tc` impairment, router agent, measurement, verdicts and result artifacts. |
| Test support | `sat-teleop-testkit` | `crates/testkit` | Shared test helpers, dev-dependency only, added only when two crates reuse a helper. |
| L3 | `sat-teleop-vehicle`, `sat-teleop-relay`, `sat-teleop-ground` | `apps/*` | Thin entry points and concrete wiring. |
| L3 | `sat-teleop-lab-cli` | `apps/lab` | The `lab` executable. |
| Tooling | `sat-teleop-xtask` | `xtask` | Layers check and fixtures. |

Rules the checker enforces: dependencies point downward only, L1 siblings never depend on each other, applications and tooling cannot be depended on, `sat-teleop-testkit` is a dev-dependency only, `sat-teleop-policy` avoids MAVLink, HTTP, SQLite and async-runtime crates, GStreamer is limited to `sat-teleop-media` and apps, and every package opts into workspace lints. It cannot prove that code avoids I/O through `std`; review covers that.

The recording boundary is deliberate: media produces bounded snapshots, detail owns indexing, retention and transfer, and policy decides quota and eviction. Apps wire these together.

## Data paths

Video. The vehicle captures from a camera or a fake source, stamps each frame with an in-picture identity and capture time, encodes H.264 and sends RTP/UDP through WireGuard to `10.77.0.1:5004`. The relay ingests it with GStreamer and publishes it locally to MediaMTX (RTSP path `live`). The ground adapter pulls it, decodes it, judges each frame's freshness from its stamp and marks it (overlay and state stamp), re-encodes it and delivers it to QGroundControl over local UDP; the output keeps coming while the source stalls, so stale, frozen or unverifiably aged video is never shown as live. QGroundControl can instead play MediaMTX's RTSP stream directly: lower latency, no indication.

Feedback. The vehicle probes the relay on `10.77.0.1:5006/udp` every 250 ms; the relay answers each probe with what its ingress received. The vehicle adapts bitrate, resolution and frame rate with the ladder in `sat-teleop-policy`, which receives time and observations as arguments ("Adaptation" below).

MAVLink telemetry. The autopilot (SITL) talks to the companion. The companion sends MAVLink to mavlink-router at `10.77.0.1:14550/udp`, which routes to the ground at `10.77.0.3:14551/udp`; the ground adapter passes it to QGC at `host.containers.internal:14550` and hears QGC's replies on the same socket. mavlink-router routes and filters only; leases, freshness and bandwidth enforcement stay in Rust.

Control envelope. QGC's commands go to the ground adapter, its only command endpoint. Read-only traffic goes raw through mavlink-router; everything that changes the vehicle travels only in JSON envelopes over UDP on the WireGuard overlay (ground `10.77.0.3:7701`, vehicle `10.77.0.2:7700`) while the adapter holds the vehicle's control lease, and is refused by the adapter otherwise. The vehicle owns the lease, validates every envelope on its own clock, and only then writes to SITL ("Control protocol" below).

Detail retrieval. Live video and recording are separate from retained detail. The vehicle periodically writes full-resolution JPEG snapshots named `<capture_ms>-<frame_id>.jpg` (written as `.tmp`, then renamed, recovered by directory scan). Jobs are submitted to the relay's HTTP job API (`:8080`, below), polled by the vehicle and returned by outbound upload, so the vehicle has no public listener. Retrieval must not block live video or control: "Retained detail" says how.

Ports and addresses above are the testbed's. The job API listens on the relay's overlay address `10.77.0.1:8080` (the vehicle) and its `ground_net` address `192.168.232.20:8080` (the ground and `checks`), and on no other.

## Control protocol

Bench only: control reaches ArduRover or ArduCopter SITL, or a logging sink, and nothing else (`crates/control/AGENTS.md`, "Bench safety"). The vehicle sends control frames (envelopes and setpoint refreshes) to its autopilot only after the autopilot has reported `SIM_WIND_SPD`, a parameter only simulator builds have (ArduPilot 4.7.2 registers the `SIM_` group under `AP_SIM_ENABLED`, which is set for the SITL board and for no other board but a ChibiOS build with the simulation linked in), and its heartbeat has told the gate which vehicle it is; the vehicle asks for the parameter once a second until it answers, and forgets both facts when the autopilot disconnects. The parameter counts only from the system and component of the heartbeat it was asked of, and a heartbeat from another address or vehicle type clears it. Until then, and for a normal flight controller build, liveness and setpoint frames are logged and counted (`sunk`) and never written, and a discrete command is answered `Rejected` with `NoDestination` (the lease stays), which the ground turns into a denied `COMMAND_ACK` for QGroundControl. The raw read-only traffic is unaffected. The decision is `identity::control_target`.

Identity. One controller at a time holds the vehicle's control lease. A controller is its overlay source address; `peer` in a lease request is informational. The vehicle takes requests and envelopes only from the addresses listed in `controllers` (`testbed/config/vehicle.toml`: the ground adapter 10.77.0.3 and the lab runner 10.77.0.4) and refuses anyone else `not_controller` before it reads what they sent; every envelope must come from the holder's address (`not_holder`). These source addresses are attested by the relay, not by WireGuard end to end: the vehicle's only WireGuard peer is the relay, with `AllowedIPs = 10.77.0.0/24`, and it is the relay that checks each of its own peers against that peer's `/32` before forwarding. A compromised relay can therefore send as the ground, so the address does not decide alone: every envelope, lease request and lease release is signed with the controller's Ed25519 key (`ed25519-dalek`) and the vehicle holds only the controllers' public keys, one per listed address. The relay holds neither half. The vehicle reads the public keys once, when it starts: changing or removing a key file takes effect at the next restart. What is signed starts with a constant for its kind (`sat-teleop/envelope/v1`, `sat-teleop/lease-request/v1`, `sat-teleop/lease-release/v1`) and the vehicle's id (`vehicle_id`, the same in the vehicle's and the ground's config), so a signature made for another kind of message or another vehicle verifies nowhere else. An envelope's signature covers the whole envelope, challenge and sequence number included, so the freshness rules below keep covering replay; a request's covers its nonce and a release's the vehicle's session (its epoch) and the lease. A message with no signature is refused `unsigned`, one whose signature is not its sender's over exactly these fields (another key, a changed field, another vehicle, a vehicle with no readable key for that address) `bad_signature` (a request is answered `lease_denied` with it, a release `rejected`); this check comes before every other one and before any lease state changes. A recorded lease request cannot be replayed: its nonce is the ground's millisecond clock and the vehicle refuses one that is not higher than the last it accepted from that controller (`replayed_request`; the memory is empty after a vehicle restart). A compromised relay can forge what the vehicle says to the ground (challenges, command results, telemetry and video), none of which moves the vehicle. Challenge tokens are a per-session counter: they prove freshness, not identity. The ground also asks the vehicle for its clock bound every 2 s (`ClockQuery`, answered `Clock`, to any listed controller, lease or not; `docs/measurement.md`, "Clock assumption"): the answer is not signed either, so a compromised relay could make the ground believe a small bound, which it can do to the video as well. The adapter's lease endpoints (`POST /lease`, `DELETE /lease`, `GET /status`) and every application's `GET /metrics` need a bearer token (one file per service, `vehicle.token`, `ground.token` and `job.token`, like the keys, compared in constant time, `sat_teleop_policy::token`; the ground's never leaves the ground and the relay holds only the job API's); without a token configured they listen on 127.0.0.1 only (the port is kept, the address is not), so an endpoint on a network address is never open by omission. The metrics address of a deployment is on loopback as well.

Two paths to SITL:

- Raw, lease or not: the read-only allowlist (parameter and mission downloads, stream rates, time sync, `REQUEST_MESSAGE` and friends) through mavlink-router, so observers can load the vehicle. The vehicle refuses everything else from the relay, a ground station's `HEARTBEAT` included.
- Envelopes, from the lease holder only: liveness (a ground station's `HEARTBEAT`, or nothing, which only keeps the lease), continuous (`MANUAL_CONTROL`, the setpoint QGroundControl sends from a joystick and ArduPilot takes as RC override from its ground station's system id) and discrete with a transaction id (`COMMAND_LONG` `ARM_DISARM` or `DO_SET_MODE`, exactly what QGroundControl 5.1.5 sends to arm and to set an ArduPilot mode, `MAV_CMD_NAV_TAKEOFF`, `REQUEST_MESSAGE`, and, only on a vehicle with `allow_missions`, the mission upload `MISSION_COUNT`, `MISSION_ITEM_INT` and `MISSION_CLEAR_ALL`, `MAV_CMD_MISSION_START` and a change into Auto). A ground station's heartbeat therefore reaches SITL only as lease liveness, and is never made up.

Messages are JSON, one per UDP datagram of at most 1200 bytes (larger ones are refused unread):

| Direction | Message | Meaning |
|---|---|---|
| ground to vehicle | `lease_request { peer, nonce }` | Ask for the lease. Granted unless another controller holds an unexpired one; asking again gives a new lease. |
| | `lease_release { lease }` | End it (holder only). |
| | `envelope { epoch, lease, seq, challenge, kind, mavlink, sent_unix_ms }` | `kind` is `liveness`, `continuous` or `{ discrete: { txn } }`, and `seq` counts per kind; `mavlink` base64 of one MAVLink 2 frame; `sent_unix_ms` for measurement only. |
| vehicle to ground | `lease_grant { nonce, lease, epoch }`, `lease_denied { nonce, reason }` | The answer to a request. |
| | `challenge { epoch, token, lifetime_ms }` | To the holder at once after a grant, then every 500 ms while the lease lasts. |
| | `command_result { txn, outcome }` | For every discrete envelope: `applied` (written to SITL; SITL's `COMMAND_ACK` follows in the telemetry), `repeated` (a retry of a transaction already applied, not written again), `unsupported` or `{ rejected: { reason } }`. |
| | `rejected { seq, reason }` | Any other refused envelope, release or unreadable datagram. |

The vehicle checks an envelope in this order and refuses it for the first rule it breaks, changing nothing: size, JSON, its signature (`unsigned`, `bad_signature`), its frame (`malformed`), whether its kind may carry the frame (`not_allowlisted`, or `unsupported` for a discrete one), this session (`wrong_epoch`; the epoch is the vehicle's start time), the lease and its holder (`no_lease`, `not_holder`, `wrong_lease`, `lease_expired`), the challenge (`unknown_challenge` unless one of the 4 most recent, `challenge_expired` once older than its lifetime), the sequence number (strictly increasing per lease and kind: liveness, continuous and discrete each count their own, so a stop command is never refused because a setpoint sent after it overtook it on the way: `duplicate_seq`, `reordered_seq`), and a discrete envelope's transaction (`txn_conflict` for a known id with another command). Freshness is judged only on the vehicle's monotonic clock, by the challenge's age; no ground timestamp decides anything. An admitted envelope renews the lease and its frame is written to SITL at once. The newest continuous setpoint is written again whenever 200 ms pass without a newer one, until it expires. A discrete transaction runs at most once per lease: a retry with the same command (for example after its acknowledgement was lost) is answered `repeated` and is not written again, and the adapter then acknowledges it `ACCEPTED` to the station. The adapter gives a station's resend (MAVLink `confirmation` above 0) of the very same command within `ack_window_ms` the transaction of the first send, and forgets them all on any lease change. Nothing waits anywhere on the way: a stale command is refused, never queued, and a reconnect, a restart or the end of a blackout replays nothing.

The adapter answers QGroundControl itself when it cannot forward: `COMMAND_ACK` `MAV_RESULT_DENIED` for a state-changing command without the lease (or with a challenge older than its lifetime), `MAV_RESULT_UNSUPPORTED` for one no envelope may carry, and `DENIED` again when the vehicle refuses a discrete envelope. It does not acknowledge an applied command: SITL does. It never takes the lease on its own, also not after a restart or a lost lease.

Freshness numbers live in `[control]` of `testbed/limits.toml`, validated by `sat-teleop-control`. The `geo` profile's measured round trip is about 600 ms (300 ms each way):

| Number | Value | Why |
|---|---|---|
| Challenge interval | 500 ms (fixed) | How old the newest challenge the adapter holds can be when it sends. |
| `challenge_lifetime_ms` | 1500 | The 500 ms interval, plus the GEO round trip (the challenge comes down, the envelope goes up: about 600 ms), plus 400 ms for jitter and SITL stalls under qemu. Control works on GEO, and an envelope held up anywhere for about a second more than its path takes dies. |
| `setpoint_lifetime_ms` | 500 | A joystick sends at 25 Hz, so a setpoint is normally replaced within 40 ms; the 200 ms refresh only bridges gaps, two of them and a margin. Capped by the challenge's lifetime. |
| `liveness_interval_ms` | 1000 | The adapter sends liveness without a frame when it has sent nothing this long (QGroundControl's heartbeat period), so the lease does not depend on a station being connected. |
| `ack_window_ms` | 4000 | QGroundControl resends a command it retries every 1200 ms, three tries in all: the last 2400 ms after the first; plus a GEO round trip and margin. |
| `lease_lifetime_ms` | 3000 | Two lost liveness intervals and a margin. After a blackout or a dead adapter the lease is gone within 3 s and control must be taken again. |
| `throttle_release_deadline_ms` | 1825 | From the vehicle's last setpoint to SITL's throttle at zero: the setpoint lifetime (0.5 s) and `RC_OVERRIDE_TIME` (0.5 s) end the drive, the throttle slews down and telemetry carries it up. 1.25 times the worst measured (1451 ms under `geo`) plus 10 ms. The vehicle's last refresh must also come within the setpoint lifetime plus one 20 ms tick, and SITL must reach Hold (its GCS failsafe); the rover then coasts to a stop without brakes, which is SITL's physics and recorded only. |

Control under a filled uplink. Control shares one FIFO with video at the uplink (512 kbit/s under `geo`), so any video queue there delays the envelopes by the same time, and an envelope's age at the vehicle is 300 ms down, up to 500 ms waiting for the next challenge, 300 ms up, plus that queue and jitter: 600 to 1100 ms plus the queue. The lifetime of 1500 ms is therefore used up at a queue of about 400 ms at the worst phase, and envelopes were refused from queues of about 200 ms (the probe that reads a queue samples it every 250 ms, and an envelope waits behind the peak). The decision is to keep the queue below that margin, not to widen the lifetime or judge the age net of a queue: an envelope that waited in a queue is older by that queue, and a vehicle that excused it would accept commands that old from a relay that held them. The freshness guarantee is therefore unchanged: an envelope counts only with a challenge at most `challenge_lifetime_ms` old at the vehicle. What keeps the queue below the margin is the vehicle's side, where the excess waits instead of in the network ("Pacing a climb" and "The pacer" under Adaptation). What remains is a queue the vehicle cannot see yet: the first try of a rung with no uplink measured, which comes at the start and after a route change, and a real drop of the uplink, which fills the queue by about the round trip times the relative drop before the controller sees it. Envelopes refused in those few seconds are refused (`challenge_expired`), never delayed: a refused setpoint for over 0.5 s brakes the copter and refused liveness for 2 s lands it, which is the failsafe working as designed.

SITL stops on its own when the vehicle stops refreshing (`testbed/sat-teleop.parm`, loaded after the pinned `rover.parm`; names and ranges checked against ArduPilot `fb773567896014da007bca58358704d4a0d8516f`): `RC_OVERRIDE_TIME 0.5` ends a `MANUAL_CONTROL` override 0.5 s after the last one (default 3 s), and the GCS failsafe (`FS_GCS_ENABLE 1`) switches to `FS_ACTION 2` (Hold) once no heartbeat or `MANUAL_CONTROL` came from the ground station's system id for `FS_GCS_TIMEOUT 2` s plus `FS_TIMEOUT 1` s.

Measurement hook. Envelopes carry `sent_unix_ms`, the ground's wall clock; the vehicle records it with its own arrival and write times for the last continuous and discrete envelope, and `lab check control-freshness` reports discrete acknowledgement times and continuous setpoint delay per profile. The testbed's containers share one clock (`docs/measurement.md`); across machines this needs a clock mapping.

## Predictive display

The ground's freshness output draws, into a frame it labels `LIVE` or `LOW RATE`, a hollow, dashed ring where the camera's centre will point when a command sent now takes effect, and, for a camera fixed to the frame, a dashed horizon. Inputs: the autopilot's newest `ATTITUDE` (the ground bridge keeps it with its receive time), the frame's age as the state stamp carries it, the uplink delay (half the round trip of the controller's newest clock query, while that reading is fresh) and `[camera] hfov_deg` and `tilt_deg`. `sat_teleop_policy::predict` turns the yaw and pitch rates times (age plus delay) into pixels with the field of view, and, for a camera fixed to the frame (`tilt_deg` set), the horizon from roll, pitch and the camera's mount tilt; a gimbal that holds its own angle gets no horizon; `mark` draws them in dashes below the stamp rows.

It never makes old video look current. Nothing is drawn unless the state is Live or LowRate and the age is known, the attitude is at most 1 s old and `hfov_deg` is configured. The mark is an outline in dashes, drawn before the label, and the label and its age are unchanged. The prediction ignores lens distortion and is clamped to the picture. Unmeasured: how close the ring lands on a real flight.

## Adaptation

The vehicle adapts its live video to the uplink, latency first: it keeps the uplink queue empty, and raises picture quality only once the delay is back at its base. A remote driver needs the newest picture more than a sharp one.

```text
vehicle (sat-teleop-vehicle)                                        relay (sat-teleop-relay)
  probe {seq, sent_mono_us} every 250 ms  --- uplink --->    10.77.0.1:5006
  <--- downlink ---  report {probe_seq, echo_sent_mono_us, window_ms,
                             rx_bytes, rx_packets, lost_packets, jitter_ms}
  round trip on its own clock -> controller (sat-teleop-policy::adapt) -> rung -> sender (x264, caps)
                                 budget (sat-teleop-policy::budget)    -> telemetry cap (sat-teleop-control)
```

Feedback. Every 250 ms the vehicle sends the relay a probe inside WireGuard; the relay answers at once with what its ingress received since its previous answer (`crates/media/AGENTS.md`, "Feedback"). The vehicle times the round trip on its own monotonic clock against its own record of the probe, so no clock is shared; an answer that is malformed, over 512 bytes, from anyone but the relay, or to a probe older than one already answered changes nothing. `lost_packets` is the relay jitter buffer's lost minus late, so reordering (which `geo` causes now and then) is not loss.

Ladder (`testbed/ladder.toml`), best first; the ladder file starts the vehicle at the second rung, the encoding it used before adaptation (the testbed overrides it with `--start-rung 0`, so checks that need the top rung do not wait for a climb):

| Rung | Group | Size | Frame rate | Bitrate |
|---|---|---|---|---|
| 0 | normal | 1280x720 | 15 | 1200 kbit/s |
| 1 | normal | 640x360 | 15 | 500 kbit/s |
| 2 | constrained | 640x360 | 8 | 250 kbit/s |
| 3 | constrained | 480x270 | 5 | 120 kbit/s |
| 4 | awareness only | 320x180 | 2 | 50 kbit/s |
| 5 | awareness only | 320x180 | 1 | 25 kbit/s |

A rung's bitrate is the most video x264 may send in any one second, keyframes included, so x264 gets the rung's bitrate times 1000 / (1000 + one frame period in ms): at 15 fps 94 %, at 2 fps two thirds and at 1 fps half of it. The slow rungs therefore send about half to two thirds of their nominal rate; an encoder that bounds a keyframe some other way could give them more. Headers come on top: each RTP packet carries 122 bytes of RTP, UDP, IPv4, WireGuard and Ethernet headers, and x264's sliced threads put each frame in about six packets, so at 15 fps the headers alone are about 11 kB/s.

Controller (`sat-teleop-policy::adapt`, `crates/policy/AGENTS.md`):

- Queue delay, the primary signal: the smaller round trip of the last two answers minus the smallest of the last 10 s. One late answer is jitter, two in a row are a queue.
- Above 150 ms and rising: the uplink carries less than is sent, so what it carried (the video the relay received, plus what the vehicle sent besides in the share of its video that arrived, all on the wire) is its capacity. Cut at once to the best rung that fits 75 % of it after the budget's reserve, so the rest drains the queue at a quarter of the uplink's rate, and let that capacity bound the climb for 30 s, doubling for a rung each time a climb to it fails. Standing without falling at all: cut one rung. Not falling at all after a cut: the cut changed nothing, so the base delay grew (a route change, or a new impairment profile in the testbed): take the cut back and count round trips from then on. Falling, however slowly: hold, so the queue drains without the ladder overshooting. The trend is the least-squares slope of the queue delay over the last second of probes sent since the last change.
- One answer more than 300 ms late (twice the threshold; jitter never comes close) is a deep queue: cut at once, without waiting for the trend or the change interval. Any answer 300 ms late pauses the video until an answer shows the queue gone, with the cut when one is due, otherwise at the rung it has: also within the change interval, so a queue that keeps growing after a cut is caught, and while a cut's headroom drains it more slowly than a pause would. Video sent while the cut's spare quarter drains the queue would arrive late by the queue for about four times its length; paused, the whole uplink drains it and the first new frame, a keyframe, arrives fresh. The answers to probes sent before the pause come back through the queue and measure the uplink again, more cleanly than at the cut, whose relay windows may reach back to before the queue, and the video resumes at the rung that measurement fits. A delay that does not drain while paused was no queue but the base growing: the video resumes and the base-shift rule takes the cut back.
- Loss in GCC's bands (draft-ietf-rmcat-gcc-02, section 6): below 2 % a rung up may come, above 10 % one rung down, in between hold; read only over at least 500 packets, so `lte-bad`'s random bursts do not pin the ladder.
- One rung up after 10 s of healthy answers (queue delay at most 80 ms, loss low or unknown), at most one change every 2 s (a deep queue aside), and no answer for 3 s falls to the floor. Unless the last answer showed a deep queue, that silence is an outage: 2 s of healthy answers after it bring back the rung before it, or the best below it that the capacity measured at the last cut carries; like a climb, a jump back that is cut within a dwell doubles that rung's hold, so a link that can no longer carry the rung is not overshot after every outage.

Pacing a climb. A queue builds for about a round trip before the vehicle sees it (600 ms under `geo`, and the probe that shows it waits in it), so a rung the uplink cannot carry peaks at about the round trip times the excess over the uplink: the 1280x720 rung, which costs 240 % of the 512 kbit/s `geo` uplink, peaked at 589, 617 and 929 ms in three climbs (`sim-flight geo` runs 1793588432518, 1793587951607 and 1793616684672), long enough to refuse the control envelopes (below). So while the uplink measured at the last cut is remembered, a climb into a rung that costs more than 110 % of it is held to a ceiling: the rung starts at 110 % of the uplink, and after each 2 s of healthy answers in which the uplink carried nearly all the ceiling allows, the ceiling goes up by 10 %, until it reaches the rung's own bitrate (`probe` in the vehicle's recent changes; it is no rung change and not counted as one). A source that sends less than the ceiling shows nothing about the uplink, so its ceiling stays. A cut within a dwell of a climb or of a raise fails the rung and doubles its hold, whether or not the cut measured the uplink. The measurement is kept, however old, until a later cut measures the uplink again or a base shift (a route change) clears it: with nothing measured, at the start or after a base shift, the first try of a rung is blind. (Forgetting it after 5 minutes was tried: on a link that cannot carry the rung, every climb after that was blind and drained again, a queue spell about every 5 minutes.)

The pacer. A ceiling only holds the encoder; the packets still leave as they come, and a keyframe, an encoder that follows a new bitrate one frame late or a source that suddenly sends more can put more into the network's queue than the controller allowed. So the sender ends in a pacer (`crates/media/AGENTS.md`): the RTP packets go into a backlog of the vehicle's own and leave from a token bucket at `Controller::pace_bytes_per_s` (`sat-teleop-policy::pace::rate`): at least the wire cost of the bitrate the controller allows the current rung (its ceiling while a climb into it is paced, else its own), so the pacer never contradicts the controller, and at most 120 % of it, the slack a keyframe and x264's one-frame buffer need, and within that 110 % of the uplink the controller believes in, the capacity measured at the last cut or the most it has tested since (each raised ceiling, the rung's bitrate once reached). A burst the router would queue otherwise peaks at the round trip times the excess: with the pace 141 % of a 512 kbit/s `geo` uplink a `sim-flight` run peaked at 392 ms (1793623580419). The belief goes up with every raise, so a recovered link is not held at the uplink of the cut; with nothing measured the pace is the 120 %. (A pace anchored only at the uplink measured at the last cut was tried: after a dip it held the video far below a recovered link and the frames it dropped read as loss, which cut the rung again; so does a pace under what the encoder is told to send.) Only video goes through it: the control endpoint, the probes and the telemetry use other sockets and never wait behind it. The backlog is bounded by age, not bytes: a frame that would wait over 150 ms behind the backlog (below the 200 ms at which envelopes were refused) is dropped whole, and so are the delta frames after it until a keyframe fits, and the first drop asks the encoder for a keyframe. A frame that is longer than that at the pace, a keyframe at a slow rung, is not dropped for it: the limit is on what is ahead of it. Video that cannot keep up is dropped and mended at a keyframe by the freshness rules of the sender, never queued, in the vehicle or in the network.

Budget (`sat-teleop-policy::budget`). The uplink budget is the uplink as the relay received it, not the profile's rate, which the vehicle cannot know. From the capacity measured at a cut the budget reserves, in order: control, the probes and the control endpoint's challenges at their largest sizes on the wire (about 1.1 kB/s), or what the vehicle measures of its probes and every control reply when that is more; telemetry, two and a half times the frame bytes SITL offers over the last 5 s (about 800 B/s, so about 2 kB/s: the bucket holds twice SITL's once-a-second burst, since the vehicle state spends it first and bulk messages only its upper half), at least the vehicle's state at 1 Hz (200 B/s) and at most the `[telemetry]` cap of 8000, plus the headers of the datagrams the vehicle measures it sending (about 30 a second, 3.3 kB/s); retrieval, the allowance (`[retrieval]` of `testbed/limits.toml`) while a job runs and zero while idle; and video gets the rest. Once a capacity is measured, the telemetry cap is that share less the headers, so telemetry never competes with video, and a burst SITL offers (a parameter list) raises the share at once. Until the uplink is measured the cap is the configured 8000.

Rungs in the sender (`crates/media/AGENTS.md`). A new bitrate takes effect at x264's next frame, at once on a cut, without waiting for a keyframe: GStreamer 1.26's `x264enc` marks `bitrate` and `vbv-buf-capacity` changeable while playing and calls `x264_encoder_reconfig` before its next frame (`gst-inspect-1.0 x264enc`; `gstx264enc.c`, `gst_x264_enc_set_property` and `gst_x264_enc_encode_frame`). A new size or frame rate goes into the rung's capsfilter; upstream renegotiates, and `x264enc` closes and reopens its encoder for the new format (`gst_x264_enc_set_format`), which starts with a keyframe. x264's VBV buffer is one frame period, the smallest it allows, and its bitrate the rung's times 1000 / (1000 + that period in ms), so any one second, a keyframe included, carries at most the rung's bitrate. Keyframes come every 2 s by time, forced with an upstream force-key-unit event, because `key-int-max` counts frames and cannot change while x264 runs. The vehicle reports the rung requested and when, and the first frame stamped once it applied (`requested`, `applied` in its metrics).

Freshness. At one or two frames a second the ground's output shows `LOW RATE` instead of `LIVE` (`docs/measurement.md`, "Freshness output").

Thresholds, `[adapt]` of `testbed/limits.toml`, validated by `sat-teleop-media`:

| Number | Value | Why |
|---|---|---|
| `probe_interval_ms` | 250 | A queue shows only when a probe that waited in it comes back: about a round trip (600 ms under `geo`) plus the queue plus up to one interval after the queue starts. At a 512 to 128 kbit/s step with the top rung's 50 kB/s offered the queue grows about 2 s a second, so every 100 ms of interval is 200 ms more queue to drain; at one probe a second the cut would come up to about 1.5 s later, with about 3 s more queue. Four probes a second cost about 4.9 kbit/s on the wire (154 bytes each), 8 % of the slowest step (64 kbit/s). |
| `min_rtt_window_ms` | 10000 | Longer than a queue lasts: at the 128 kbit/s step the queue built and drained within about 7 s (`bandwidth-steps` runs), so the base stays the empty-queue round trip while it drains. A route change inflates the queue delay for at most this long, and the cut it causes is taken back within about 3 s. |
| `queue_delay_high_ms` | 150 | About 2.7 times the worst healthy queue delay measured (55 ms under `lte-bad`, whose jitter is 30 ms pareto each way; `geo` up to 48 ms). One answer late behind a 720p keyframe (147 ms at 512 kbit/s) does not count: the filter takes the smaller of two answers 250 ms apart, and keyframes come 2 s apart. A single answer more than twice this late, over five times the worst healthy one, is a deep queue. |
| `drain_above_ms` | 300 | Twice `queue_delay_high_ms`, the deep queue jitter never reaches. Frames sent behind a queue this deep arrive at least 0.6 s old under `geo` (320 ms plus the queue), at the stale threshold. At the 512 to 128 kbit/s step the oldest frame was 674 ms with the pause at 300 ms (`bandwidth-steps` runs on cf21fa5) and 1.7 s with it at 500 ms (1793551927349 on caae26f, where the queue drained with the video running). Validated above `queue_delay_high_ms`. |
| `queue_delay_base_ms` | 80 | 1.25 times the worst healthy queue delay (55 ms) plus 10 ms: a healthy streak restarts at any answer above it, so it must clear the jitter or the ladder would never climb under `lte-bad`. |
| `trend_window_ms`, `trend_ms_per_s` | 1000, 100 | Over four answers the filtered queue delay of a healthy link moves with its jitter, about 30-40 ms a second; 100 ms a second is about three times that. A queue drains at (capacity minus rate) / capacity seconds a second; after a cut fitted to 75 % of the capacity it drains at 250 ms a second, at least twice the threshold (validated: `trend_ms_per_s` at most half of (100 - `capacity_fit_percent`) x 10), so a correct cut reads as draining. |
| `capacity_fit_percent` | 75 | A cut fitted to the whole measured uplink drains the queue at a few per cent, slower than jitter lets the trend tell, which read as standing and could be taken back as a base shift. At 75 % the measurement's own error (a few kB/s at 128 kbit/s) stays inside the margin. |
| `loss_window_ms`, `loss_min_packets` | 10000, 500 | `lte-bad`'s Gilbert-Elliott loss averages 5 % in bursts of about 4 lost packets, entered from 1.26 % of packets. Over n packets the bursts are about Poisson(0.0126 n), and loss above 10 % needs more than 0.025 n of them: a 13 % chance at 50 packets, 4 % at 200, 1.2 % at 500. A loss reading therefore needs 500 packets, none older than 10 s; below that loss says nothing, and the slow rungs (under 50 packets a second) are guarded by delay alone. |
| `loss_low_percent`, `loss_high_percent` | 2, 10 | GCC's bands: below 2 % increase, above 10 % decrease, in between hold. |
| `stale_after_ms` | 3000 | Twelve probe intervals. `lte-bad` loses a probe or its answer about one time in ten, so even a second without an answer is rare while the link is up; three seconds is an outage, or a queue the delay rule has cut long before. Before the first answer the start rung stands: the relay may not be up yet, and the vehicle would send that rung anyway. |
| `outage_recovery_ms` | 2000 | After a fall to the floor that no deep queue led to: eight answers at the base in a row show the link back. An outage says nothing about the uplink, so the rung before it returns at once, no higher than the capacity measured at the last cut carries, instead of a rung every dwell (about 50 s from the floor to 640x360 at 8 fps under `outage-10s`). |
| `dwell_ms` | 10000 | Each rung up doubles the rate or more; ten seconds of healthy answers come before each. |
| `min_change_interval_ms` | 2000 | One change at a time, each given the time to show. |
| `capacity_hold_ms`, `capacity_hold_max_ms` | 30000, 300000 | A rung up into an uplink that cannot carry it builds seconds of queue before the cut, so the capacity measured at a cut bounds a climb to a rung that does not fit it for 30 s. Each time a climb to a rung is cut within a dwell, that rung's hold doubles, counted from that cut (60, 120, 240 s), up to 5 minutes, so a link that cannot carry it is probed less and less often (`geo-degraded` probed once a minute with a fixed hold); a later cut that measures at least 10 % more uplink than at the failure gives the rung its 30 s back (capacities measured at the same step spread about 7 % around their mean). |

## Retained detail

The vehicle keeps what the operator may want to look at again: a JPEG of the source's frame, at the source's full size, every second. An operator who saw something in the live picture asks for the frame captured some seconds ago, whole or a rectangle of it, and gets it labelled as historical: the retained frame's id and capture time, never the live one's.

```text
sender (sat-teleop-media)                      vehicle app                      relay                    ground
 source -> convert -> tee -> scale/rate -> ... live   (unchanged)
                        \-> queue(leaky,2) -> videorate 1 fps -> jpegenc q90 -> appsink(drop)
                                                |  try_send (queue of 2: full = snapshot dropped, counted)
                                                v
                                       writer thread -> store: <capture_ms>-<frame_id>.jpg  (retention: policy)
                                                                  ^ nearest at or before, crop (image), q80
   poll GET /jobs/next (5 s)  <-- overlay 10.77.0.1:8080 --> job table (4 jobs, 2 MiB)  <-- 192.168.232.20:8080 -- POST /jobs, GET /objects/{id}, DELETE /jobs/{id}
   PUT /jobs/{id}/chunks/{n}, POST /jobs/{id}/complete|fail --->
```

Store. `<capture_ms>-<frame_id>.jpg` in a directory on a volume of its own, written as `.tmp`, synced and renamed. A start scans the directory, deletes the `.tmp` files a crash left, indexes the valid names, leaves every other name alone and trims to the limits; gaps (consecutive snapshots further apart than `gap_after_ms`, a restart for one) are reported in the metrics. Retention (`sat-teleop-policy::retention`): a byte quota, a maximum age and a free-space floor on the volume, oldest first, and a snapshot a retrieval is reading is pinned until the pin runs out. The snapshot's capture time is the wall clock when its frame passed the branch and its frame id the one the live stream's next frame carries then, so it lies within a frame of the live frame of that name; the live stamp is drawn on the live branch's copy, never in the snapshot.

Positions and outage snapshots. A snapshot is written with where the vehicle was: the bridge keeps the autopilot's newest `GLOBAL_POSITION_INT` (latitude, longitude, altitude above home, heading) with its receive time, and `sat-teleop-policy::position::fresh` hands it over only when it is at most 2 s old, so a silent autopilot never lends a stale fix; a snapshot with no fresh position has none. An autopilot sends only what it was asked for, so while the bridge has no fresh position it asks for `GLOBAL_POSITION_INT` every 500 ms itself (`SET_MESSAGE_INTERVAL`, again every 5 s until one arrives), whether or not a ground station ever connected. The position, and the mark below, are a small `<capture_ms>-<frame_id>.pos` file written before the JPEG, so a snapshot never appears without them; a snapshot with neither is just the JPEG, which is how every earlier store reads. A snapshot taken while the ground is not heard (the relay has not answered a probe within `stale_after_ms`, the test that already holds retrieval) is marked as an outage snapshot. Retention keeps marked snapshots past `max_age_s` and the byte quota, newest first, up to `outage_share_percent` of `max_bytes` (default 50), and for `outage_keep_s` (default 3600) from capture. When the share is full the older ones lose their protection and go first. A completed job that sent a snapshot releases it, and it is then ordinary. Nothing here writes to the autopilot; the position is read from telemetry the bridge already forwards.

Listing. `detail outage` (`just detail-outage`) posts a job of kind `outage`: the vehicle answers with the marked snapshots captured since a time, oldest first, at most 16, with their positions, as JSON to `POST /jobs/{id}/listing` (the ground reads it from `GET /objects/{id}`). A fetched snapshot carries its position in the `X-Position` header, and `detail fetch` prints it.

Sightings. With the detector on, each person it finds while the ground is not heard (the same test that marks outage snapshots) becomes a sighting (person or any other configured kind) in a list in the vehicle bridge's stats, `sat-teleop-policy::sighting`: the capture time of the frame (the frame's age on the vehicle's monotonic clock taken off the wall clock), the kind, the drone's fresh position, altitude and heading, the box in picture fractions and the score. A detection made with no fresh position is not recorded. A detection that comes within 2 s of a sighting's last one, with its box centre within 0.15 of the picture of that sighting's, is the same one, if it is of the same kind (a car and a person in one place are two sightings): it extends the sighting's time range and moves its box, and two boxes of one frame are never merged. The list holds the newest 256 and drops the oldest: a person who stays in view is one entry, so 256 is hundreds of separate people or passes, a few tens of kilobytes. The detector thread only takes the list's lock for a moment and never waits on the link. When the ground is heard again the bridge sends each unsent sighting up from the autopilot's system and component as one `STATUSTEXT` (severity INFO, at most 50 characters: `car 59.32931 18.06862 12m 14:02:31`, starting with the kind, latitude and longitude to five places, altitude in whole metres above home, the UTC time it was first seen), oldest first, at most one every 500 ms, and only from the upper half of the telemetry bucket that the autopilot's own telemetry shares, never while replies wait (`RateCap::take_bulk`); a sighting that finds no room waits and is marked sent only when its frame went out. Sent sightings stay in the list so the ground can still list them. `detail sightings` (`just sightings`) posts a job of kind `sightings`: the vehicle answers with the sightings first seen since a time, oldest first, at most 16, each with the retained snapshot nearest in capture time (looked up when listed and within 1.5 s, so one taken just after the detection counts), as the `sightings` of the same `POST /jobs/{id}/listing`. The snapshot is then fetched like any other (`detail request --at-ms`). Nothing here writes to the autopilot.

Job API. Every request needs the bearer token (`401` without or with another one; the relay starts the job API only with a token), and the listeners are bound where they are needed, the vehicle's on the overlay and the ground's on `ground_net`, each answering only its own routes, and on no other address. One token is shared by the vehicle, the ground and the relay: it keeps strangers on a network out, it does not tell the vehicle from the ground (the route split and the firewall do). Each request is checked as hostile once it has been read: URLs at most 200 bytes, JSON bodies 4 KiB, chunks 16 KiB, a declared length over the limit refused unread, unknown JSON fields refused; job ids are 16 bytes from the operating system's random source as 32 hex digits and nothing else names a job, a file or a path; `max_bytes` at most 1 MiB, `expires_in_ms` 1 s to 10 min, at most 4 jobs and 2 MiB of `max_bytes` between them, whatever their state; a chunk's index below `max_bytes / 512`, its SHA-256 checked on arrival and the whole object's at the end, the object's size and the JPEG's checked against the metadata, duplicates (the same bytes are a retry); the vehicle's long poll admits one poll at a time. What is not bounded: `tiny_http` 0.12 reads the request line and the headers with no limit on a line's length or on the number of headers, and starts a thread for every connection, so the 200-byte URL check runs after the line has been read in full. A client that stalls its head holds a connection thread; one that stalls its body, or reads a response slowly, holds one of the four workers of its listener, as there is no read or write timeout. The job API shares the relay process with the live ingress and the RTSP publish, so a flood on `ground_net` or the overlay can exhaust that process, not only the API. It must move to a process of its own, or sit behind a proxy that limits sizes and times, before it faces an untrusted network. Requests: `POST /jobs {kind: snapshot|crop, at_capture_ms, crop?: {x,y,w,h} as fractions, max_bytes, expires_in_ms}` answers `{job_id}`; `GET /objects/{id}` answers 202 while the vehicle works, 410 with its reason when it failed, and the JPEG with `X-Capture-Ms`, `X-Frame-Id`, `X-Crop` (pixels of the source, or `none`) and `X-Source-Size`; `DELETE /jobs/{id}` cancels and frees the slot.

Vehicle. It takes the oldest queued job, validates it again (it never trusts the relay: a rectangle outside 0 to 1 or without area fails the job, and `crop::pixel_rect` keeps every crop inside the picture), picks the nearest retained snapshot at or before `at_capture_ms`, pins it, and sends it as stored or decoded, cropped and encoded again at quality 80. The upload is one chunk at a time, each hashed, paced by a token bucket at the allowance; the chunk is what the allowance carries in half a second (512 B to 16 KiB). A job ends done, cancelled (the relay no longer knows it: the next chunk finds out), expired (its life, counted from when it was taken) or failed (with a reason the ground can read).

Live first. Retrieval may not add latency to live video or control. (1) It sends only when `sat_teleop_policy::retrieval::permit` allows: a non-zero allowance, the ladder at a `Normal` rung, no drain, the relay's feedback fresh and showing no queue (queue delay at most `queue_delay_base_ms`); a queue is the first sign retrieval costs the video, so it stops itself on one, and a chunk waits (the job pauses) until the conditions return or the job expires. (2) It stops within one chunk: the conditions are asked before every chunk, and at most one is in flight. (3) What it may send is the allowance, in wire bytes per second, which the vehicle's adaptation reserves in its uplink budget while a job waits to send: the controller fits the video to the measured uplink after control, telemetry and retrieval, so a cut leaves room for it. The reserve is granted only when the rung fitted to the share less the allowance is still a `Normal` one; otherwise it is zero and retrieval is held. That is decided from the measured capacity, not from whether retrieval is sending, so the reserve cannot push the video out of `Normal` and return when retrieval stops. (4) The snapshot branch cannot delay the live branch: a leaky queue in front of it, an appsink that drops, a writer thread that may be slow, and a snapshot queue of two that drops a snapshot, counted, when storage cannot keep up. `lab check retrieval` grades the live frame age with and without retrieval, in two passes under the same profile.

Failures. An error in the snapshot branch (`jpegenc` or the appsink) propagates through the tee and restarts the live pipeline, so only a misconfigured snapshot quality or rate can trigger it today. A vehicle that crashes mid-job leaves the job Assigned on the relay until it expires (at most its `expires_in_ms`, and it holds one of the 4 slots meanwhile); the ground's `DELETE` frees it. While retrieval is held, the vehicle learns that a job was cancelled only at its next chunk or when the job expires.

On a Pi, `jpegenc` at full resolution once a second runs next to the H.264 encoder and costs CPU there. `docs/measurement.md` records its cost in the testbed, which is not a Pi; it is unmeasured on one (`docs/pi.md`, "Snapshot cost"). The branch holds at most one camera buffer: a leaky queue of one, and a copy of the one frame a second that is kept.

## Regional video

The link carries a fixed number of bits a second, so the picture is spent where it matters: the part the pilot boxed in QGroundControl, and any person or vehicle a small detector finds, stay sharp, and the rest is softened before it is encoded. The softened area costs the encoder fewer bits, which the sharp regions get.

```text
QGC: TRACK_RECTANGLE to camera 100 -> ground adapter -> signed Region envelope (own sequence counter, lease and challenge as liveness)
                                                              | overlay
vehicle control loop: sets the pilot's box in RegionCell (never forwarded to the autopilot)
                                                              |
sender: source -> tee -> scale/rate -> I420 rung -> soften outside RegionCell::regions(), outline detections and the followed box -> stamp -> encoder
                     \-> (every 500 ms) scale to 320x320 RGB -> detector thread (vehicle app) -> RegionCell detections
                     \-> (10 a second) scale to 320x180 luma -> tracker thread (vehicle app) -> RegionCell followed box
```

- Pilot's box. QGroundControl asks the adapter's camera for a tracked rectangle; the adapter sends it to the vehicle every 500 ms in a `Kind::Region` envelope (`docs/qgc.md`). The vehicle answers with the box the sender actually keeps sharp, or none: a box too large (over `max_area_percent` of the picture), crowded out by detections, older than `pilot_ttl_ms` or with softening off (`soften_factor` 1, the default) is not confirmed. The box is dropped at once when the lease is released, expires or is granted again. The tracking status is active while the vehicle confirms the box (3 s after each confirmation) or a crop of it arrived in the last 30 s (`served_box` in the camera component), so with softening off it is the crops that keep the pilot's red box up.
- Detail on demand. While a box is tracked the ground (`apps/ground/src/box_detail.rs`) asks the relay's job API for a crop of the box, widened 10 % on each side and clamped to the picture (`inset::widen`), from the newest retained snapshot every 4 s, one job in flight, and keeps the newest decoded and scaled to fit a third of the output's width (`media::inset::Image`, `DetailCell`) with its capture age. A request goes through the retrieval path of "Retained detail" unchanged: its allowance, pacing and `permit` rules stay as they are and there is no priority path. A new box, STOP_TRACKING or a lost box empties the cell, and a crop fetched for a box no longer tracked is dropped.
- The inset never makes old video look live. The output draws it only into a frame whose state is `Live` or `LowRate` and only while the crop is under 30 s old (`sat_teleop_policy::inset::place`, a pure function with a table test); in `Stale`, `Frozen`, `Disconnected` or `AgeUnknown` frames it is not drawn, so a lost link takes it away with the live picture. It is drawn after the predictive ring and before the labels, never over the stamp rows, in a 2 px frame of its own, with its own label `DETAIL <age> s` (the age at the moment of drawing, the age it arrived with plus the time held, so a step of the wall clock never makes it younger), beside the live label which keeps stating the live picture's age; the live picture is never replaced, only covered in one corner. Nothing in this reaches the autopilot: the crop comes from the relay's job API and the box goes to the vehicle only as the region envelope that already existed.
- Follow. With `[region] follow = true` in the vehicle config the box the pilot draws is only where a follow starts. The vehicle follows that part of the picture from frame to frame with a small correlation tracker (`sat_teleop_policy::follow`) on a fourth, leaky branch of the tee: the luma plane at 320 x 180, `follow_fps` frames a second, newest frame wins, so a slow tracker drops its own frames and never holds the live video. The start snaps to a detection the box overlaps by more than half. The template is the pixels of the start, matched by normalised cross-correlation in a window around the last place, so brightness and contrast changes do not matter; it moves a little towards each good match (0.7 or better), so a target that slowly changes its look keeps its score, and never learns from a worse one. The followed box is outlined in its own colour (pink, F tab), is what `RegionCell::regions` keeps sharp and what the vehicle confirms to the ground, and is pushed to the lease holder as it moves (at most four times a second), so QGroundControl's red box and the detail inset's crops (`Camera::target`) follow the target instead of staying where the box was drawn. Lost means lost: when the match stays under `follow_min_score` for `follow_lost_frames` frames in a row, the target reaches the picture's edge, or the start box is too small or flat, the follow ends. The outline goes, the vehicle sends `ToGround::Lost` once, the ground drops the tracked box so the tracking status goes idle, and nothing resumes until the pilot draws a box again; the box is never guessed from where it was. Nothing in this moves the drone. Cost and the choice of tracker: `docs/measurement.md`, "Following".
- Detector. Off unless the vehicle config has `[region] detector`; it works with softening off, when it only outlines what it finds. NanoDet-Plus-m 320 through `tract-onnx` runs at `detector_fps` on frames from a third branch of the tee that is leaky and holds one buffer, so it can only drop its own frames. `detector.kinds` in the same table picks what counts, from person, bicycle, car, motorcycle, bus, truck and boat (the COCO classes 0, 1, 2, 3, 5, 7 and 8; the default is `["person"]`, an unknown name is refused at load); a cell is the best scoring wanted class, and overlapping boxes of any kinds keep the better one. What it finds counts as regions for `detection_ttl_ms`; the sender outlines each in its kind's colour (people amber) with a one-letter tag in a solid tab at the box's top-left corner (P, B, C, M, U for bus, T, S for boat), both scaled with the picture's width; a box too small for the tab gets the outline alone. A model that does not load shows as `detector.state` `failed: <cause>` and the video is unaffected.
- Softening. Off by default; `[region] soften_factor` of the vehicle config turns it on (2 to 4). Blocks of `soften_factor` x `soften_factor` luma pixels (half of it on chroma) outside every region are replaced by their average, on the rung-sized frame, before the stamp is drawn: the stamp, and so the age, is exact. A region keeps its place across rung changes because it is a fraction of the picture.
- Bound. Softening takes detail away and adds none; at most `max_regions` regions are kept, and when they cover more than `max_area_percent` of the picture nothing is softened. A region envelope carries no MAVLink frame (one that does is refused `not_allowlisted`) and nothing in this feature adds a path to the autopilot. Cost on emulated hardware (`docs/measurement.md`, "Regional video check"): softening a frame took 0.8 to 2.0 ms at p95, one detector run 29.4 ms at p95 at the Pi 4's limits, and the vehicle process used 4.8 to 6.6 % of a host core with the box tracked.
- Measured: cost is small (above), but on the lab's test card softening did not gain: its SSIM changed by -0.016 to +0.003 pilot only, and the outside scored 0.005 to 0.042 below the plain picture one rung down at the top rung (`docs/measurement.md`, "Regional video check"). The V4L2 hardware encoder has no testbed path, so its gain is unmeasured.

## Deployments

Real deployment (`docs/deploy.md`; unverified on hardware): the relay is a public VPS. Vehicle and ground both initiate outbound WireGuard connections to it. The vehicle is a native binary under systemd, the relay's three processes run in containers with host networking, and the ground adapter runs in a container next to QGroundControl.

```text
 Pi 4 + USB camera           VPS                    Ground machine
+----------------+      +-------------+        +------------------+
| vehicle app    |      | WireGuard   |        | ground adapter   |
| H.264 RTP -----+--LTE/GEO-> relay    |<-wg----+ QGroundControl   |
| detail poller  |      | MediaMTX    |        |                  |
| wg client      |      | mavlink-rtr |        | wg client        |
+----------------+      +-------------+        +------------------+
```

Container testbed: the same applications run in compose project `sat-teleop` and a router container replaces the cellular or GEO link.

```text
vehicle_net 192.168.231.0/24 (internal)
  vehicle-net sidecar .10   companion, SITL share its namespace
        |
      router .254 (also on ground_net and ctl_net)
        |   tc impairment per direction, NAT vehicle_net -> ground_net
ground_net 192.168.232.0/24
  relay-net .20  (relay, mediamtx, mavlink-router)
  ground-net .30 (ground adapter)
  checks .40     (lab runner, headless receiver)

ctl_net 192.168.233.0/24 (internal): router agent :9000 and /metrics only, never data
```

The router is the only service on both data networks. NAT means the ground side cannot initiate to the vehicle network, like carrier-grade NAT. Orchestration runs outside the impaired path. Development ports bind to host loopback; QGC runs natively on macOS and is fed through Podman port forwarding.

## Key decisions

| Decision | Reason |
|---|---|
| GStreamer through `gstreamer-rs` | Reuse capture, encode, RTP/RTCP, decode. Write coordination and policy, not media protocols. |
| One H.264 RTP/UDP uplink inside WireGuard | Standard encrypted transport, one upload regardless of viewer count. |
| Relay ingests with GStreamer, publishes locally to MediaMTX | Own the WAN receive statistics explicitly instead of assuming feedback forwarding. |
| Adaptation by queue delay first, loss in GCC's bands | Latency first: a deep queue (the testbed's 1000 packets, like real LTE and satellite links) loses nothing while it fills, so waiting for loss means seconds of backlog. Random loss that is not congestion must not pull the picture down. |
| No separate "receive rate below 85 % of send rate" trigger | The probe waits in the same FIFO as the video, so a receive rate below the send rate over probe-delimited windows is the queue delay rising, which the delay rule already sees; on short windows the comparison is noisier than the delay. The receive rate measures the capacity at a cut instead. |
| A probe every 250 ms, not every second | The probe is how a queue becomes visible; at one a second a hard rate step builds seconds more queue before the cut. |
| Telemetry's budget reserved before video | The vehicle's state outranks the picture; on slow links video gets only the floor. |
| Keyframes forced by time | x264 counts its keyframe distance in frames and cannot change it while running, so a fixed frame count would mean a keyframe every 30 s at one frame a second. |
| The relay forwards video without re-timing it | Its RTSP publisher synced to the jitter buffer: every frame waited out the buffer's latency, and after the path delay dropped the relay kept the old delay for seconds and broke P-frames. The jitter buffer now only bounds the wait for a missing packet (`docs/measurement.md`). |
| mavlink-router for routing only | Authentication, leases, freshness and bandwidth stay in Rust. |
| Unchanged QGC plus a ground adapter | QGC's passive UDP receiver cannot report adaptation feedback and its extra streams are switch-only. The adapter wraps commands and adds freshness after the WAN. |
| The ground re-encodes to show freshness; direct RTSP stays the no-indication option | QGC has no notion of video age, so the age must be in the picture. Decoding and re-encoding at zero latency adds a few milliseconds (`docs/measurement.md`); QGC's direct RTSP path skips it, and with it every indication. |
| The adapter is the vehicle's camera only while the vehicle is heard | QGC finds a MAVLink camera's stream on its own, but counts any message from the vehicle's system id as a sign of life; a camera speaking through an outage would hide QGC's "Communication Lost". |
| 600-800 ms is network RTT | An assumption until measured on a real link; not a frame-age target or a command-freshness allowance. The `geo` profile targets 550-700 ms measured RTT, with extra runs at 800 ms. |
| ArduPilot ArduRover 4.7.2 prebuilt SITL, not PX4 from source | PX4 has no prebuilt SITL and cannot practically be built in a 2 GiB VM. ArduPilot ships an official x86_64 SITL binary, which runs under qemu on Apple Silicon, and a rover suits GEO latency. If wrong, only autopilot-specific parameter names change; the gate is generic MAVLink. |
| Detail starts as periodic JPEG snapshots, not SQLite or video segments | Simpler, crash-safe, enough for snapshot and crop retrieval. Clip retrieval would need a later segment store. |
| Synchronous threads and bounded `sync_channel` queues | No async runtime unless a task proves it necessary. |
| Control envelope as JSON over UDP on the overlay, not MAVLink TUNNEL | Simpler and no 128-byte payload limit. mavlink-router carries telemetry and raw MAVLink only. |
| Controller identity is the overlay source address, from a configured list | The relay checks each WireGuard peer's `/32` before forwarding, so no second key system for the bench; a compromised relay could pose as the ground, which keys between controller and vehicle would stop. Challenge tokens only prove freshness. |
| Command freshness from vehicle-issued challenges, judged on the vehicle's clock | No clock sync between ground and vehicle is needed, and a command that sat anywhere dies by its challenge's age. |
| Continuous control is `MANUAL_CONTROL`, refreshed by the vehicle only while fresh | It is what QGroundControl sends from a joystick and what ArduPilot takes as RC override with its own timeout; SITL's GCS failsafe and override timeout stop the rover when refreshing stops. |
| No commands to real actuators | Control goes to SITL once it has identified itself by a SITL-only parameter, otherwise to a logging sink, so no configuration can point it at a real autopilot by mistake; a physical vehicle needs its own interlocks and a separate decision. |
| The vehicle is a native binary on the Pi, the hardware encoder where there is one | A container costs memory a Pi Zero 2 W (512 MB) lacks. Stamping needs raw pixels, so the only decode is an MJPEG camera's; H.264 is never decoded and encoded again. |
| The relay is a host-networked container set behind a per-peer firewall | The job API's bearer token keeps strangers out; the source address of the tunnel peer is what separates the vehicle's port from the ground's. The relay never transcodes, so it fits a small server. |
| Plan and status in GitHub, not committed files | Issue #2 is the spec of record; the repository holds code and documentation of behaviour. |

## Measurement principles

The lab measures independently of the application's adaptation decisions and never derives an application pass threshold from the impairment it applied. The one exception is calibration: the boot check compares measured overlay RTT with the profile's configured delay, because its job is to prove the impairment is in effect. The adaptation check compares what the vehicle offers the uplink with the cap the profile applied, because staying below it is what adaptation is for; the vehicle itself never learns the profile. A run writes `results/<run-id>/summary.json` and `timeseries.csv` and exits 0 for pass, 1 for fail, 2 for incomplete or ungraded; a missing measurement is never a pass. Frame age uses a stamp burned into each frame at injection, because RTP timestamps are relative media time. Within the testbed all containers share one clock; across machines a clock mapping and its uncertainty are required.

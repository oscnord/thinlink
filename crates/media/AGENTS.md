# AGENTS.md: crates/media

`sat-teleop-media` (L1) owns the GStreamer pipelines of the live video path, the ground's freshness output, media feedback between the vehicle and the relay with the vehicle's adaptation loop, and the JSON metrics endpoint the applications serve. It depends on `sat-teleop-policy` for the in-picture stamp, the state stamp and freshness, and on no other workspace crate. See the root `AGENTS.md`, `docs/testbed.md` and `docs/measurement.md`.

## Pipelines

All built from element factories (no launch strings, so no config value is ever parsed as pipeline syntax).

- `sender`: source (`videotestsrc is-live=true pattern=ball`, at the configured `width` x `height` when given, or a y4m file paced by `clocksync` and looped with a flushing seek at its end, since `y4mdec` cannot do segment seeks (with `still = true`: its first frame held by a live `imagefreeze`, no loop, which `lab check regional` uses for its card), or an ingest, below) -> `videoconvert` -> `tee` -> `videoscale` -> `videorate drop-only=true` -> I420 rung capsfilter -> stamp probe -> `queue leaky=downstream max-size-buffers=2` -> `x264enc tune=zerolatency speed-preset=ultrafast bframes=0` -> `rtph264pay config-interval=1 pt=96 mtu=1200` -> `appsink sync=false` -> the pacer (below) -> UDP to the relay. It runs the rung last requested (`SenderStats::request`), and a request changes the running pipeline: `bitrate` and `vbv-buf-capacity` (both changeable while playing; x264 reconfigures before its next frame), and for a new size or frame rate the rung capsfilter's caps, which upstream renegotiates and which make `x264enc` reopen its encoder with a keyframe. x264's VBV buffer is one frame period and its bitrate the rung's times 1000 / (1000 + that period in ms), so any one second carries at most the rung's bitrate, keyframes included. `key-int-max` counts frames and cannot change while x264 runs, so the stamp probe forces a keyframe every `keyframe_interval_ms` by time (an upstream force-key-unit event) and `key-int-max` only bounds the distance at 60 fps. A request changes the running pipeline outside the lock the stamp probe takes for every frame (new caps renegotiate through the streaming thread). `requested` (rung, its number, time) and `applied` (rung, the number of the request it applied, the first frame stamped in its shape, the monotonic time since the request, time) are in the metrics.
- `sender` sources for real cameras (`camera.rs`; none has run on hardware, `docs/pi.md`): `kind = "v4l2"` is `v4l2src device=...` -> capsfilter with the configured `format` (`mjpeg`: `image/jpeg`, decoded by `jpegdec`; `yuyv`: raw `YUY2`), size and rate -> the sender's `videoconvert`; `kind = "libcamera"` is `libcamerasrc` -> a size and rate capsfilter. `camera::plan` (format to media type, raw format and decoder) is the tested pure part. `probe` lists the video sources of a `gst::DeviceMonitor` with their caps (`sat-teleop-vehicle probe-camera`). On a `v4l2` source the stamp's capture time is the capture buffer's own: a probe on `v4l2src`'s src pad (`camera::watch_capture`, before the decoder) turns each buffer's age (pipeline running time minus its timestamp) and offset (the driver's sequence number) into a capture time in `CaptureClock`, and a buffer with the sequence number of the one before keeps the old time, so a camera that repeats a frame is read `Frozen` by the ground. The stamp probe reads it for the buffer it is marking (both run in the same streaming thread, with no queue between the camera and the stamp: never add one there). Other sources stamp `unix_ms()` at the stamp. Not run against hardware.
- `sender` encoder: `encoder = "x264"` (default) or `"hardware"` in the vehicle config; `camera::choose_encoder` picks `v4l2h264enc` only when `hardware` is asked for and the element factory exists (GStreamer registers it only on a board with the encoder), else `x264enc`. `v4l2h264enc` gets `extra-controls` (`video_bitrate`, `repeat_sequence_header=1`, `h264_i_frame_period`) and a `video/x-h264,profile=main,level=4` capsfilter after it; a rung change sets `extra-controls` again (`set_bitrate`). Stamping needs raw frames, so nothing is ever decoded from H.264 and encoded again; an MJPEG camera is the only decode. Never decode H.264 on the vehicle.
- `sender` pacer (`sender/pacer.rs`): the appsink's callback copies each RTP packet into a backlog of the vehicle's own and a thread sends them to the relay from a UDP socket, so the video never goes out faster than `SenderStats::set_pace` says (`Controller::pace_bytes_per_s`, set at every answer). Admission is `sat_teleop_policy::pace::Admission`, decided on the first packet of each frame (the first with another presentation time): a frame whose backlog ahead would take longer than 150 ms at the pace to leave is dropped whole, so are the delta frames after it until a keyframe fits, and the first drop asks the stamp probe for a keyframe (`keyframe_wanted`), so stale video is dropped and the picture mends at a keyframe, never queued. The thread waits on a `TokenBucket` with a 20 ms burst (at least two packets). Control, liveness, challenges, telemetry and the probes are sent by other sockets and never wait behind it. `pace_bytes_per_s` and `paced_dropped` are in the metrics.
- `sender` snapshot branch (`[snapshot]`, `fps` 1-10 and `quality` 1-100; none without it): the tee's second branch takes the source's frames at the source's size: `queue leaky=downstream max-size-buffers=1` -> `videorate drop-only=true` -> framerate capsfilter (a probe here copies the kept frame, so a camera's small buffer pool is never held while a JPEG encodes) -> `jpegenc quality=...` -> `appsink max-buffers=2 drop=true sync=false`. The queue is leaky and sits in front of everything else in the branch, so the branch can never hold the live frames back; the stamp is drawn on the live branch's copy (a buffer the tee shares is copied on write), so snapshots carry none. A probe after the rate notes the time and `SenderStats`' next frame id for each frame by presentation time, and the appsink callback pairs the JPEG with it (`Snapshot { capture_ms, frame_id, jpeg }`, the id the live stream's next frame carries at that moment, so within one frame of the live frame of that name) and hands it to the caller with `try_send` on a bounded `sync_channel`: a full queue, a slow disk behind it, drops the snapshot and counts it (`snapshots.dropped`; `taken` and `unidentified` are the others), never a live frame. `sat-teleop-media` does not know the store; `sat-teleop-vehicle` runs the writer.
- `sender` regional video (`region.rs`; limits in `[region]` of `testbed/limits.toml`, validated by `RegionSettings::validate`; `soften_factor` is in `[region]` of the vehicle config, 1-4, absent or 1 is off and `validate_soften_factor` refuses the rest. With it off the pilot's box has a ttl of 0 (never kept or confirmed) and detections are still outlined; `softened_frames` counts only frames that were softened):
  - Order in the stamp probe: read `capture_ms`, then `Regional::shape` softens the picture outside `RegionCell::regions()` (`policy::soften`, plane by plane) and outlines the detections in amber (Y 210, U 16, V 146, 2 px at 640 wide, scaled with the width), then the stamp is drawn. The stamp is never softened. The pilot's box is not drawn; QGroundControl draws it.
  - The regions come from `RegionCell`, which the vehicle's control loop shares: the pilot's box, the detections and the limits. The control loop confirms to the ground the pilot box `RegionCell::pilot_in_use()` returns, so a box the sender drops (too large, crowded out, softening off) is never reported as applied. Never compute the regions anywhere else.
  - Detector branch (only when `[region] detector` is in the vehicle config and its model loaded: the vehicle loads it before the sender starts, and builds no branch otherwise): the tee's third branch, `queue leaky=downstream max-size-buffers=1` with `copy_frames` thinning to `detector_fps` and copying, `videoscale` -> `videoconvert` -> RGB `input` x `input` capsfilter -> `appsink max-buffers=1 drop=true sync=false`. The callback copies the frame into a `DetectorFrame` and `offer`s it, replacing the one still waiting: a busy detector skips to the newest frame and never holds the live video. The detector runs in `sat-teleop-vehicle` (`sat-teleop-detect` is a sibling crate that media cannot depend on); it publishes with `Regional::detected`. A model that does not load sets `detector.state` to `failed: <cause>` and the video goes on.
  - Metrics: `region` (`active` in the last frame, `softened_frames`, `shape_failures` (frames that could not be shaped and went on with their stamp), `soften` stage percentiles) and `detector` (`state`: `off`, `running` or `failed: <cause>`, `runs`, `people`, `ms` stage percentiles).
- `sender` ingest (`kind = "ingest"`, `listen`, `from`; `ingest.rs`):
  - Chain: leaky `appsrc` (512 KiB, do-timestamp) -> `rtph264depay` -> `h264parse` -> `avdec_h264 thread-type=slice output-corrupt=false` -> the sender's `videoconvert`. Keep it free of jitter buffers and frame threading: the decode is the only latency added before the stamp.
  - Keep `output-corrupt=false`: a picture broken by loss must be dropped, never stamped as fresh.
  - Accept datagrams only from addresses in `from` (`ingest::accepts`, IPv4-mapped counts as IPv4) and count the rest as `refused`. Never take a source from the packet's content.
  - Time decodes with pad probes keyed by buffer PTS (`ingest` metrics: `packets`, `refused`, `frames_decoded`, `decode_ms_*`). Never pair input and output by order: the decoder drops frames.
  - The camera sends no B-frames, so PTS stays unique per frame.
  - The reader stops when the run ends (`Handles` drop); keep the socket released for the restart.
- `ingress`: `udpsrc` bound to the overlay address -> `rtpjitterbuffer latency=50 drop-on-latency=true` -> `rtph264depay` -> `h264parse config-interval=-1` -> `rtspclientsink protocols=tcp` (its internal sinks set to `sync=false`).
- `receiver`: a `Source` -> `rtph264depay` -> `h264parse` -> `avdec_h264 thread-type=slice` -> `videoconvert` -> (`videoscale`, for a fixed size) -> I420 -> `appsink sync=false max-buffers=1 drop=true`; a pull loop reads the stamp and the state stamp of each sample. With a fixed size, a probe on `videoconvert`'s output reads them before scaling, at the size they were drawn at, and the pull loop takes them by presentation time: scaled, a stamp's blocks leave the grid the reader samples (a 1280-wide stamp scaled to 640 has 26.5-pixel blocks, a 480-wide one 26.7, where the reader expects 26). `receive` sends each `Observation` to a bounded `sync_channel` (the lab); `decode` hands it to a callback with the sample (the ground). Sources: `Rtsp` as QGC plays RTSP (`rtspsrc latency=80 drop-on-latency=true protocols=udp`), `RtspTcp` for the ground's pull from MediaMTX (`rtspsrc latency=0 protocols=tcp`: nothing is lost or reordered on TCP, so the jitter buffer passes every packet at once), `Rtp` as QGC plays a MAVLink camera's RTP/UDP stream in low latency mode (`udpsrc` with RTP H.264 caps, no jitter buffer).
- `output` (the ground): `decode` of `RtspTcp` at the output size into a latest-only slot; the output thread takes each new frame at once (a decoded picture older than the newest one, a decoder concealing a loss with an earlier frame, is not shown, nor one whose stamp is unreadable while the state is Live or LowRate, so an old or broken picture never carries the newest frame's state), or, when nothing went out for two output periods (`2/fps`) or the state may change sooner (`freshness::next_change_ms`), repeats the last frame (a black slate before the first), draws the state stamp and pushes it: `appsrc is-live=true do-timestamp=true max-buffers=1 leaky-type=downstream` -> `textoverlay` (bottom-left, white while live, amber at a low rate, red otherwise; a probe on its video sink pad sets the text and colour from each frame's own state stamp in the streaming thread, so a label never lands on another frame, and a frame without a readable state stamp reads `NO STATE`) -> `x264enc tune=zerolatency speed-preset=ultrafast bframes=0 threads=2` -> `rtph264pay config-interval=1 pt=96 mtu=1200` -> `multiudpsink sync=false` to every destination. The state is decided before the encoder and the sender, so each current (Live, `LowRate`) frame carries, in its end offset, the moment on the pipeline's clock when `next_change_ms` says the state may change; the overlay probe hands it to a probe on the sender's sink pad, which (`freshness::LabelDeadline`) drops the frame if it leaves after that moment, counts it in `late` and asks the encoder for a keyframe, so a stall in the encoder or sender never sends old video as Live. This leans on the encoder holding nothing back (`zerolatency`: one frame in, its packets out, in the same thread). With `[camera] hfov_deg` (`CameraConfig`) and a `Predictive` the output also draws `sat_teleop_policy::predict::mark` into each current frame (aim ring and horizon, `mark::draw`) right after the state stamp and before the overlay, so the label is drawn over it; the inputs are read per frame and any missing input draws nothing. The state comes from `sat_teleop_policy::freshness::classify` with what a `Tracker` saw: when the last frame arrived, the newest frame with a new stamp (capture time later than any before, age 0-60 s), the source's frame interval (`freshness::cadence_ms` of the newest new frames' ids and capture times; it changes with the vehicle's rung), and how many of the frames that arrived in the last second (a window of time, not of frames) had a readable stamp. The wall clock is read once per frame, at decoding; the newest frame's age later is its age then plus the monotonic time since, so a wall-clock step cannot make a stale picture look young.

## Adaptation (`adapt`)

The vehicle's loop: a probe to the relay every `probe_interval_ms`; each answer to an outstanding probe whose echo matches becomes `sat_teleop_policy::adapt::Feedback` (the round trip on the vehicle's monotonic clock; received and lost video packets; the uplink on the wire: the video the relay received over at least its last 500 ms of windows, plus the vehicle's telemetry, control replies and probes over at least its last second, since SITL sends its telemetry in one burst a second, each datagram with `sat_teleop_policy::budget::DATAGRAM_OVERHEAD`, and when the video arrived slower than it was sent, or was paused for a drain, taken in the mix the vehicle sent (its rest against its video over the newest second it sent video throughout): a queue lets every kind of traffic out in the share it came in, so counted as sent the rest overstated a queued uplink by up to a third; unmeasured until there is that much), and the controller's decision goes to `SenderStats::request`; the controller starts from the rung the sender runs, so a loop restarted after a failure agrees with it; a drain also pauses the video at the stamp probe (`SenderStats::set_draining`) until the controller resumes it or the loop starts again, and the first frame after asks for a keyframe, since the relay drops packets that waited too long in the queue. The controller is also asked at every probe without an answer, so silence counts. An answer that is malformed, over 512 bytes, from anyone but the relay, or to an unknown or older probe changes nothing (`refused`). The budget's usage is measured from the same readings: the telemetry SITL offered over at least the last 5 s, its datagrams, and the probes and control replies on the wire over at least the last second. The telemetry cap, `Budget::telemetry_cap` of the controller's capacity, goes to the caller whenever it changes. `LadderConfig` is `testbed/ladder.toml` (each rung validated as a sender rung, the ladder's order by `sat-teleop-policy`), `AdaptLimits` is `[adapt]` of `testbed/limits.toml` (durations 1-600000 ms, base below high, drain above high, the trend window and the stale threshold spanning two probes, the change interval within the dwell).

## Feedback (`feedback`)

The relay answers each probe from the vehicle (`Probe { seq, sent_mono_us }`, on 10.77.0.1:5006 inside `WireGuard`) at once with a `Report` of what the ingress received since its previous answer: `probe_seq`, `echo_sent_mono_us`, `window_ms`, `rx_bytes` and `rx_packets` (RTP, headers included, as `udpsrc` received them), `lost_packets` (the jitter buffer's lost minus late: lost on the way, not merely reordered) and `jitter_ms`. JSON, one message per datagram, at most 512 bytes (`decode` refuses larger ones unread); anything else, and probes from any address but the configured vehicle's, is dropped and counted (`refused`). The ingress copies the jitter buffer's counts every 100 ms, so each answer's loss is current.

## Invariants

- Low latency first: no element may add buffering beyond the fixed jitter buffer latencies above; sinks never sync, queues are small and leaky, the encoder has no B-frames or lookahead. `videorate` only drops: duplicating needs the next frame first, which held every frame for one interval before the stamp, invisible to the measurement.
- The relay forwards, it never re-times: every sink created inside the ingress pipeline (the ones `rtspclientsink` makes) gets `sync=false`. Synced, they held each frame until the jitter buffer's timestamp plus its 50 ms latency, and after the path delay dropped they kept the old delay for seconds, stalled the jitter buffer and broke P-frames (`docs/measurement.md`). The jitter buffer's latency is now only the longest wait for a missing packet.
- RTP packets are at most 1200 bytes so they never fragment inside WireGuard (MTU 1420).
- Every pipeline failure is a typed `MediaError` from the bus (error or EOS) or from building; `supervise` restarts after one second and `Health` records runs and the last error, so a failed pipeline never looks healthy.
- A pipeline is set to `Null` when its run ends (`Running` drop), so a restart can bind its sockets again.
- Frame ids come from `SenderStats` and keep increasing across pipeline restarts, and so does the requested rung: a restarted sender starts at it.
- The sender's `SourceMode` (test only, set by `sat-teleop-vehicle`'s debug hooks): `Live` stamps every frame; `Paused` drops frames at the stamp probe, before the encoder, so the encoder's reference chain stays intact and the stream resumes without waiting for a keyframe; `Frozen` stamps the first frame after the switch and then sends a copy of it, stamp and all, in place of every frame (on the new frame's timestamps).
- The output never resamples to a fixed clock: a decoded frame goes out as soon as it arrives, and a repeat only when nothing went out for two periods or the state is due to change, so a source frame arriving a little late does not meet a repeat in the encoder and every change of state shows on time. Its source and output pipelines restart separately; while the source is down the output keeps going (`Disconnected`). It holds the newest decoded buffer and copies it for each frame it sends, so the state stamp never touches the decoder's buffer.
- The stamp is drawn after scaling and before the encoder queue; `capture_ms` is the wall clock at that moment. Frames the stamp cannot be drawn into are counted (`stamp_failures`), never dropped silently.
- Rungs are validated before use: even dimensions up to 3840x2160 that fit the stamp, 1-60 fps, 8-50000 kbit/s, keyframes every 100-60000 ms. The output's encoding is a rung that must also fit the state stamp (4 rows of blocks); `FreshnessLimits` (`[freshness]` of `testbed/limits.toml`) are 1-60000 ms, with the stale and frozen thresholds below the disconnect one.
- `metrics::serve` answers only `GET /metrics`, one request at a time, without reading bodies.

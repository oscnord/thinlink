# AGENTS.md: crates/control

`sat-teleop-control` (L1) owns MAVLink between the autopilot and the ground stations: the vehicle bridge with its command gate, telemetry budget and control endpoint, the ground bridge with its controller and camera component, and the control envelope protocol between them. It depends on `mavlink` (default features off: `std` and `dialect-ardupilotmega`, which includes `common`; the vehicle is ArduPilot), `serde_json` `base64` (already in the lockfile through `ureq`) for the envelope and `ed25519-dalek` for its signature, and on `sat-teleop-policy` for the token bucket and the control lease, and on no other workspace crate. It builds natively (no GStreamer). See the root `AGENTS.md`, `docs/architecture.md` ("Control protocol") and `docs/testbed.md`.

## Bench safety

The vehicle bridge talks to one autopilot: `autopilot` of `[mavlink]` is `tcpout:<loopback ip>:<port>` (SITL, which runs in the vehicle's network namespace: `VehicleConfig::validate` refuses a TCP address off loopback) or `serial:<device>:<baud>` (a flight controller on `/dev/ttyACM0` or `/dev/serial0`; `Autopilot` parses it and `serialport` opens it).

Control frames (envelopes, setpoint refreshes) go to the autopilot only when `identity::control_target` says `Autopilot`, and it says so only when `identity::failures` (the one place that decides, one table test) is empty; otherwise they go to the logging sink: logged with the reasons (first, then every 600th), counted as `sunk` and never written, and a discrete command is answered `Rejected` (`NoDestination`, lease kept), so the ground sends QGC `MAV_RESULT_DENIED`. The failing interlocks and their reasons are in the metrics (`mavlink.control.interlocks`). In `mode = "sitl"` (the default) the only interlock is the identity: the autopilot's heartbeat has told the gate its vehicle type and it has reported `SIM_WIND_SPD`, a parameter only SITL builds have (`identity` cites ArduPilot's source). In `mode = "real"` the autopilot must not be SITL (it reports no marker after `REAL_PROBES` probes; `sitl_in_real_mode`, which exists only with the `testbed` cargo feature and which the vehicle's loader refuses unless `debug_hooks` is set, lets tests run it against SITL), every controller must have a public key that loaded when the vehicle started (`key_errors`; keys are read once, so a change to a key file waits for a restart), and the failsafe parameters of `[mavlink] require` must have been read back from the autopilot's own system and component within 30 s, in the required type (`type` of each `require` entry) and equal the required values (or, for an entry with `compare = "bits_set"`, have every bit of its value set and the others free, which is how a bitmask such as `FS_OPTIONS` is required) (`params`: `PARAM_REQUEST_READ` one parameter at a time, each read again after 10 s; a missing, stale or different one refuses control, and so does an empty required set). With `allow_missions` in real mode the loader also refuses a `require` that lacks (`params::validate_missions`, `MISSION_RULES`): `FS_OPTIONS` `bits_set` 3 (continue in Auto on the radio and GCS failsafe: a lost link stops the sticks too) and `bits_clear` 16 (or the GCS failsafe is skipped in the stick modes), `FENCE_ENABLE` 1, `FENCE_TYPE` `bits_set` 3 (altitude and circle, which need no upload), `FENCE_ALT_MAX` `at_most` a value up to 120, `FENCE_ACTION` 1 (RTL or Land) and `BATT_FS_LOW_ACT` `at_least` 1 (the battery failsafe is what ends a mission that runs long). Other `compare` forms: `bits_clear` (every bit of the value clear in the reading), `at_most` and `at_least` (a NaN reading fails both). The autopilot's actual values are then compared as for any entry. Once all hold, liveness (the ground station's heartbeat) reaches the autopilot as it does for SITL, so `FS_GCS_ENABLE` keeps its meaning. The bridge asks for the marker with `PARAM_REQUEST_READ` once a second until it answers, and, while it has no fresh position, for `GLOBAL_POSITION_INT` with `SET_MESSAGE_INTERVAL` every 5 s (`identity::stream_request`, the one other request it makes of its own), using the heartbeat's system and component; `learn_vehicle` reads both from the autopilot's own stream. SITL disconnecting forgets what was learned. The marker and the readings are stored with the system and component of the heartbeat they were asked of (`identity::Autopilot`, `ControlStats`): a heartbeat from another address or of another vehicle type clears the marker and the probe count and the probe starts over, and a `PARAM_VALUE` from another system is ignored.

## Modules

- `frame`: CRC-valid MAVLink 1 and 2 frames of `ardupilotmega`, read with `mavlink::MavlinkReader` from a stream or a datagram and kept byte for byte. Bytes that form no such frame (noise, truncation, a bad CRC, a message id the dialect does not define) are skipped. Never hand-roll framing.
- `gate`: what may reach the autopilot, and how. `decide(&MavMessage)` is the raw allowlist the vehicle applies to everything from the relay, lease or not, so observers can load the vehicle: `PARAM_REQUEST_LIST`, `PARAM_REQUEST_READ`, `MISSION_REQUEST_LIST`, `MISSION_REQUEST_INT`, `MISSION_REQUEST`, `MISSION_ACK`, `REQUEST_DATA_STREAM`, `TIMESYNC`, `SYSTEM_TIME`, and `COMMAND_LONG`/`COMMAND_INT` with `MAV_CMD_REQUEST_MESSAGE`, `SET_MESSAGE_INTERVAL`, `REQUEST_PROTOCOL_VERSION` or `REQUEST_AUTOPILOT_CAPABILITIES`. `HEARTBEAT` is not on it: a ground station's heartbeat reaches SITL only as lease liveness. `SYSTEM_TIME` is admitted although ArduPilot may set its real-time clock from it (that is how QGC gives a vehicle without GPS the date); it changes no flight state, but it is the one admitted message that writes something. `wrap` and `admits` say which envelope kind may carry a message: a ground station's heartbeat (`MAV_TYPE_GCS`) as liveness, `MANUAL_CONTROL` as continuous, and as discrete only `COMMAND_LONG` with `MAV_CMD_COMPONENT_ARM_DISARM`, `MAV_CMD_DO_SET_MODE` (exactly what QGroundControl 5.1.5 sends to arm and to set an ArduPilot mode, which is also how it lands, returns and brakes a copter, `docs/qgc.md`), `MAV_CMD_NAV_TAKEOFF` (its copter takeoff), `MAV_CMD_MISSION_START` (how QGroundControl 5.1.5 starts a mission from the ground; it sends `MISSION_SET_CURRENT` only to jump to an item, which stays refused) or `MAV_CMD_REQUEST_MESSAGE`, and the mission upload messages `MISSION_COUNT`, `MISSION_ITEM_INT` and `MISSION_CLEAR_ALL`. The upload messages, `MISSION_START` and copter mode 3 (Auto) are admitted by the vehicle only with `allow_missions = true` in `[mavlink]` (off by default; `refused` takes the switch): otherwise they are refused `mission_not_allowed` (Auto: `mode_not_allowed`, as before). With the switch on, an upload message or start is still refused for anything but a copter and for any mission type but the waypoint mission, so a ground station cannot rewrite the fence or rally points over the link. An item must be one of waypoint, takeoff, land, return to launch, `NAV_LOITER_TIME`, `NAV_LOITER_TURNS`, `DO_CHANGE_SPEED` or `CONDITION_DELAY` (anything else could undo the fence, a mode, a servo or a relay: `mission_item_not_allowed`). A mission must end, so there is no unlimited loiter and no `DO_JUMP` (a loop, or nested jumps, multiplies what any cap allows), and the hold of a waypoint, a timed loiter and a delay (param 1) is at most 300 s and of a counted loiter at most 10 turns (`hold_refused`; NaN and negatives refused too), and an item with a location must be relative to home (`MAV_FRAME_GLOBAL_RELATIVE_ALT`), above it by 0 to 120 m (above 0 but for a landing). No item may have `current` above 1: `ArduPilot` takes 2 as a Guided goto and 3 as an altitude change, outside the mission, whatever the seq (`GCS_MAVLINK::handle_mission_item`, `GCS_Common.cpp`, `fb773567`). Item 0, the home placeholder, may have any frame and altitude but must be a waypoint, since `ArduPilot` never reads what it is sent for it (`AP_Mission::replace_cmd`, `read_cmd_from_storage`, `fb773567`). A `MISSION_COUNT` above 48 items is refused `mission_too_long`: every item is a transaction and the vehicle remembers 64, so a longer upload would push an arm or takeoff transaction out of its memory. This needs mavlink's `mav2-message-extensions` feature, which carries `mission_type`. A raw mission message from the relay is still refused by `decide`. `vehicle_of` reads the vehicle type (`Copter`, `Rover`) from an `ardupilotmega` heartbeat, and `refused` is the one pure decision for the discrete commands that pass: a `DO_SET_MODE` is refused unless the type is known and param 1 is exactly `MAV_MODE_FLAG_CUSTOM_MODE_ENABLED` and param 2 a whole mode on the type's list (copter: Stabilize 0, AltHold 2, Guided 4, Loiter 5, RTL 6, Land 9, PosHold 16, Brake 17; rover: Manual 0, Hold 4, RTL 11), and a copter change into Stabilize, AltHold, Loiter or PosHold is refused without a fresh `MANUAL_CONTROL` setpoint from the lease holder (`LeaseState::setpoint`); a `NAV_TAKEOFF` is refused unless param 7 is a finite number above 0 and at most 120 m. `COMMAND_INT` and the `SET_MODE` message never reach it: the first has no envelope kind and the second is dropped. `route` is the ground's split: read-only raw, the rest in an envelope, answered by the adapter (a state-changing command no envelope may carry) or dropped. Unknown ids and values fail closed.
- `auth`: Ed25519 signing with `ed25519-dalek` of envelopes, lease requests and lease releases. `Signer` (a controller's private key) and `Verifier` (a public key) are made for one `VehicleId`; the signed bytes are a constant per message kind, the vehicle's id, then the payload (an envelope's JSON with `sig` left out, a request's nonce, a release's epoch and lease). `Verifier` answers `Refusal::Unsigned` or `Refusal::BadSignature`; the vehicle checks before any lease state changes. Signing returns an error, never an empty message to sign. Keys are one line of base64 (32 bytes) in a file; `generate` writes `ctl-<name>.key` (mode 600) and `ctl-<name>.pub` and keeps an existing private key (`lab keygen`, run by `just lab-keys` and `just deploy-keys`). The vehicle verifies before any other check on an envelope; a controller whose key file cannot be read is listed in `key_errors` and has all its envelopes refused. A private key file that the group or others can access is refused (`KeyError::Mode`, the fix in the message). Never hand-roll anything here: no key derivation, no comparison of signatures.
- `clock`: `ClockSource` (`chrony`, `chrony_at` a host whose chronyd command port answers, `shared`, `fixed`) and `Clock`, a machine's clock bound at runtime. `Clock::poll` runs `chronyc -c [-h host] -m 'timeout 1000' 'retries 0' tracking` (chrony 4.6 has no `-t`) every 2 s on a thread of its own, or, for `fixed`, compares the wall clock with the monotonic one (`policy::clock::fixed_holds`): a step beyond the bound ends it until restart; `sat_teleop_policy::clock` derives the bound and ages it. `Injection` (test hooks only) replaces it. The vehicle answers `ToVehicle::ClockQuery` from any listed controller with `ToGround::Clock { nonce, bound_ms }` (none without a fresh bound); the ground's `Controller::ask_clock` asks every 2 s and `GroundStats::refresh_bound` adds the two bounds every 100 ms into an atomic that `GroundStats::clock_bound` reads without a lock for the freshness output (the output loop must not wait for the controller's mutex). In real mode the vehicle also needs its own fresh bound before it first sends control (`Interlock::ClockBound`, gating the start only: `Clock::started` latches the first fresh bound, `Facts::clock_started`, and a stale bound afterwards only reaches the label and the log) and the loader refuses `shared` and `fixed` there unless `sitl_in_real_mode` is set. The answers are not signed (`docs/architecture.md`, "Control protocol").
- `ground` keeps the autopilot's newest `ATTITUDE` (component 1 only, not the camera's) with its receive time (`GroundStats::attitude`, on `monotonic_ms`) and the uplink delay (`Controller::uplink_delay_ms`: half the round trip of the newest clock query, none once that reading is stale) for the predictive display (`docs/architecture.md`). The delay is not a measurement of control envelopes themselves.
- `envelope`: the protocol (`docs/architecture.md`): `ToVehicle` (`Envelope { epoch, lease, seq, challenge, kind, mavlink, sent_unix_ms, sig }`, `LeaseRequest`, `LeaseRelease`, `ClockQuery`) and `ToGround` (`Clock`, `LeaseGrant`, `LeaseDenied`, `Challenge`, `CommandResult`, `Rejected`) as JSON, one per datagram, at most 1200 bytes (`decode` refuses larger ones unread as `oversize`). `mavlink` is base64 of exactly one MAVLink 2 frame of the dialect (`frame`), or absent in a liveness envelope that only keeps the lease. `sent_unix_ms` is for measurement only. `Refusal` is every reason as one enum, the policy's included, in snake case on the wire and as metric keys; `ends_lease` says which ones end the controller's lease. No reason is ever matched as a string. `ControlLimits` is `[control]` of `testbed/limits.toml`, validated (a challenge outlives its 500 ms interval, a setpoint its 200 ms refresh, the lease two liveness intervals; nothing above 60 s).
- `telemetry`: the budget from `testbed/limits.toml` (`[telemetry]`: `bytes_per_s`, the cap, 1000-1000000; `offered_percent`, 100-1000, and `essential_bytes_per_s`, 1 up to the cap, for the uplink budget) and a class per message id, over `sat_teleop_policy::rate::TokenBucket` (one second of budget). While the vehicle has measured its uplink, its budget sets the cap from what SITL offers (`VehicleStats::set_telemetry_cap`, never below `essential_bytes_per_s`, so the vehicle state keeps flowing); the bridge applies it at its next frame. The autopilot's `HEARTBEAT` always goes out, spending the bucket when it can: a ground station declares the link lost after 3.5 s without a vehicle message, and `essential_bytes_per_s` counts it. State (`SYS_STATUS`, `GLOBAL_POSITION_INT`, `ATTITUDE`, `COMMAND_ACK`) may spend the whole bucket and is dropped only when it is empty. Replies to admitted requests (`AUTOPILOT_VERSION`, `PARAM_VALUE`, `MISSION_COUNT`, `MISSION_ITEM_INT`, `MISSION_ITEM`, `MISSION_ACK`) spend only its upper half and, when it is spent, wait in order in the one bounded queue (64 KiB of frames, 10 s; beyond that dropped as `rate_limited` or `expired`; the queue is emptied, as `expired`, whenever SITL reconnects). Everything else is bulk: upper half only, dropped when over budget and whenever replies wait. ArduPilot sends its whole parameter list (1256 values, about 46 KB) in about 0.6 s over SITL's TCP port, ten times the default budget; dropping that burst lost about three quarters of it.
- `autopilot`: the address (`tcpout:` or `serial:`, table-tested) and the open connection (`Wire`: a TCP stream, or a serial port whose clones share a closed flag, since a port cannot be shut down).
- `identity`: `control_target` (the one pure decision), the marker parameter, the probe frame and the position stream request.
- `vehicle`: the autopilot over its `Wire` (reconnect with backoff 0.5-5 s, 5 s without data counts as a hang; a 20 ms read timeout lets waiting replies out between the autopilot's frames; a serial port's writing clone waits up to 100 ms for room, `SERIAL_WRITE_TIMEOUT`) and mavlink-router over UDP. Telemetry goes up one frame per datagram within the budget; from the relay, only datagrams from its configured address are read and only what `decide` admits is written to SITL.
- `vehicle::control`: the control endpoint on the vehicle's overlay address (10.77.0.2:7700), one thread, a 20 ms receive timeout as its tick. It drives `sat_teleop_policy::control::LeaseState` with milliseconds of its own monotonic clock; the epoch is its start time in UNIX ms. Lease requests are granted or denied (`LeaseDenied { reason }`; a signed one whose nonce is not above the controller's highest accepted is `replayed_request`); the holder (identified by its overlay source address, which the relay attests, not WireGuard end to end; `peer` is informational; anyone not in `controllers` is refused `not_controller` before the datagram is read) gets a `Challenge` every 500 ms while the lease lasts, the first at once. An envelope is checked in order: size and JSON, its signature (`auth`), its frame (one MAVLink 2 frame of the dialect, else `malformed`), whether its kind may carry the frame (`not_allowlisted`; for a discrete one the outcome `Unsupported`), then the policy (epoch, lease and holder, challenge, sequence number of its kind). A refused envelope changes nothing. Only then is the frame written to SITL; a discrete command first passes `gate::refused` (the vehicle type is the latest autopilot heartbeat from SITL, unknown again whenever SITL disconnects), and a refusal is answered `Rejected` with `mode_not_allowed`, `no_fresh_sticks`, `takeoff_altitude` or `mission_not_allowed`, counted, and not recorded as a transaction. A continuous setpoint is written at once and becomes the one `LeaseState` keeps; it is written again whenever 200 ms pass without one, until it expires. A discrete envelope always gets a `CommandResult`: a retried transaction (same id, same command by `gate::CommandKey`'s digest) is answered `Repeated` and is not written again, and a known id with another command is refused `txn_conflict`; SITL's own `COMMAND_ACK` follows in the telemetry. Other refusals get `Rejected { seq, reason }`. Liveness without a frame only keeps the lease.
- `ground`: telemetry from mavlink-router (accepted only from its overlay address, whose sending port is learned) to every ground station, each through its own UDP socket. What a station sends back (only from the station's address) is decoded; a message addressed to the camera component goes to the camera, the rest is routed with `gate::route`: read-only frames go raw to mavlink-router, everything else to the controller; undecodable frames are dropped.
- `ground::camera`: when the ground config announces a camera (`camera_uri`), the adapter is the vehicle's camera component (system id the vehicle's, `MAV_COMP_ID_CAMERA` 100) for the stations. A camera `HEARTBEAT` (`MAV_TYPE_CAMERA`) follows every autopilot heartbeat to the stations; every message addressed to component 100 is the camera's and never reaches the vehicle or an envelope: `REQUEST_MESSAGE` for `CAMERA_INFORMATION` (flag `CAMERA_CAP_FLAGS_HAS_VIDEO_STREAM` only), `VIDEO_STREAM_INFORMATION` or `VIDEO_STREAM_STATUS` (stream 0 or 1), and the deprecated `REQUEST_CAMERA_INFORMATION`, `REQUEST_VIDEO_STREAM_INFORMATION` and `REQUEST_VIDEO_STREAM_STATUS` that QGroundControl alternates with on a retry, are answered `COMMAND_ACK` `ACCEPTED` and the message; any other command `MAV_RESULT_UNSUPPORTED`; anything else is dropped. The one stream (id 1, "overview") is `VIDEO_STREAM_TYPE_RTPUDP` at the freshness output's size, rate and bitrate with the configured URI, flagged running and never thermal. The camera speaks only while the vehicle is heard: its heartbeat follows the autopilot's, and it answers only within 1.2 s of any message from the autopilot (ArduPilot sends a burst every second): QGroundControl counts any message from the vehicle's system id as a sign of life, so a made-up one must never hide a lost link. Counts (`heartbeats`, `answered` by message, `unsupported`, `dropped`) are served as `camera` in the adapter's metrics.
- `ground::control`: `Controller`, the stations' only command endpoint, on the ground's overlay address (10.77.0.3:7701). `take` asks the vehicle for the lease (again, if it holds one without a fresh challenge) and waits up to 3 s for the answer and, after a grant, the first challenge; without one it reports `NoChallenge`, never a usable lease; `release` gives it back; `status` reports `LeaseStatus` (`none`, `requested`, `held`, `denied` or `lost`: the vehicle refused an envelope for a lease reason, or sent no challenge for a lease lifetime). While it holds the lease with a challenge received no longer ago than its lifetime, a station's GCS heartbeat goes out as liveness, `MANUAL_CONTROL` as continuous and an allowlisted command as discrete, with a sequence number of its kind (each kind counts its own), in a new transaction; a station's resend (`confirmation` above 0) of the same command (`CommandKey`: the whole `COMMAND_LONG` but `confirmation`) sent within `ack_window_ms` keeps its transaction, whether or not its result came, and every lease change forgets the commands sent; after a liveness interval with nothing sent, a challenge triggers a liveness envelope without a frame. Without that, a state-changing command is answered locally with `COMMAND_ACK` `MAV_RESULT_DENIED` (from the command's target system and component, which is how QGroundControl matches it) and anything else is dropped and counted. A command no envelope may carry gets `MAV_RESULT_UNSUPPORTED`. A mission upload message follows the same rules with a `MISSION_ACK` (`MAV_MISSION_DENIED` or `MAV_MISSION_UNSUPPORTED`, from the vehicle to the station) in place of the `COMMAND_ACK`, which is how QGroundControl's Plan view shows a refused upload; its transaction is never matched with a resend (QGroundControl repeats a message on its own timer, 1.5 s, and the autopilot answers a repeat), and the autopilot's own `MISSION_REQUEST` (ArduPilot asks for the items of an upload with it, not `MISSION_REQUEST_INT`: `MissionItemProtocol::queued_request_send`), `MISSION_REQUEST_INT` and `MISSION_ACK` (replies, never bulk) and `MISSION_CURRENT` and `MISSION_ITEM_REACHED` (state) come back as telemetry. A vehicle refusal of a discrete envelope becomes `DENIED` (or `UNSUPPORTED`) to the station; an applied one gets no ack from the adapter, because SITL's arrives through the telemetry; a `Repeated` one (its first ack was evidently lost) gets `ACCEPTED` from the adapter.
- `position`: `NewestPosition` keeps the autopilot's newest `GLOBAL_POSITION_INT` (from the system and component the heartbeat named; latitude and longitude both zero is no fix; a heading of 65535 is none) with its receive time, read from the telemetry the bridge already forwards. `fresh(now)` gives it only within `sat_teleop_policy::position::MAX_AGE`, and it is forgotten when SITL disconnects. It is read-only: nothing in it writes to the autopilot.
- `stats`: per-direction counters (messages and bytes in and out, drops by reason), the gate's refusals by message (`PARAM_SET`, `COMMAND_LONG MAV_CMD_DO_SET_MODE`, `undecodable <id>`; keys come from the dialect, so the map is bounded) and link state, served by the applications on `GET /metrics`.

## Invariants

- No queue towards SITL and no replay. The telemetry reply queue is the only queue, bounded by bytes and age. A frame from the relay or an envelope is written at once or refused (`no_destination` while SITL is disconnected); the adapter never holds a command to send later and never resends one on its own. A reconnect, a restart or the end of a blackout therefore cannot run an old command, and a stale envelope dies on the vehicle's clock (its challenge's age).
- Freshness is judged only by the vehicle's monotonic clock: challenge age and setpoint age. `sent_unix_ms` never decides anything.
- The adapter's own freshness check (a challenge received more than its lifetime ago is dead) only spares sending doomed envelopes; the vehicle decides.
- A failed or timed-out write to SITL (1 s) shuts the connection down and counts `send_failed`; the bridge reconnects. A partial frame left in the stream could otherwise let SITL resync inside a later frame's payload, which a ground station chooses. No retry, no queue. Writes from the relay thread and the control endpoint share the connection under one lock, so frames never interleave.
- Drops and refusals are whole messages, always counted by reason; a failed SITL connection or socket shows `up: false` with the error, never a healthy state.
- Receive errors are counted (`receive_errors` per direction) and logged once per kind, then every 600 repeats, never at the 10 Hz retry rate.
- Every input is hostile: datagrams are read into a 2048-byte buffer, envelopes above 1200 bytes are refused unread, frames come only from `mavlink`'s CRC check, and nothing indexes input without `get()`.
- Rates and budgets count MAVLink frame bytes, not UDP, IP or WireGuard headers.

## Checks

```sh
cargo test -p sat-teleop-control --locked
just lab-up && just lab-check mavlink lan && just lab-check control-freshness lan
```

Tests pin the raw allowlist and the envelope split in one table, hostile datagrams, and the reply queue against bulk and state; the lease, freshness and transaction rules and the bucket's priority floors are tested in `sat-teleop-policy`. The camera is checked end to end by `lab check qgc-status` (`camera_answered`). `vehicle::sitl_identity` runs the vehicle against a stand-in autopilot on loopback and pins that a fresh envelope is sunk until the autopilot reports the SITL marker and reaches it after; `lab check control-freshness` shows `mavlink.control.target` `sitl` on the real SITL, and `just sim-check lan` the same on the copter.
